# 后端交接说明

## 1 后端整体架构

一轮对话的主流程：

```text
用户请求
  -> 立即输出 progress_events 等待提示
  -> 输入预处理与越界检测
  -> 读取 session memory / 用户历史 / 购物车
  -> Doubao-first IntentPlan 识别复杂意图和动作序列
  -> Dialogue Flow Controller 决定业务流程
  -> 工具执行或 RAG 检索
  -> 商品过滤、重排、增强字段匹配、购物车侧个性化
  -> 构造 grounded prompt
  -> Doubao 生成最终回复
  -> 防幻觉校验与必要修复
  -> 构造 frontend_events / frontend_data / system_debug
  -> 写入本地历史与事件记忆
  -> SSE 输出正式结果和 done
```

核心代码入口：

| 模块 | 文件 | 作用 |
|---|---|---|
| API 路由 | `backend/app/api/routes/chat.py` | `/api/chat/stream` 和 `/api/chat/stream/upload` |
| Agent 主流程 | `backend/app/agents/shopping_agent.py` | 串联意图、检索、工具、回复、历史保存 |
| 意图理解 | `backend/app/agents/query_understanding.py` | 简单模板 + Doubao IntentPlan |
| 对话流程 | `backend/app/agents/dialogue_flow.py` | recommendation/filtering/comparison/cart 等流程 |
| 商品检索 | `backend/app/retrieval/` | hybrid retrieval、fallback、重排 |
| Prompt/RAG | `backend/app/rag/` | 构造给 Doubao 的商品事实上下文 |
| 回复生成 | `backend/app/agents/response_generator.py` | 导购式回复、对比、详情、购物车反馈 |
| 前端事件 | `backend/app/agents/frontend_event_builder.py` | 统一前端动作列表和数据 |
| 记忆系统 | `backend/app/memory/` | session state、短期记忆、事件记忆、用户历史 |
| 购物车工具 | `backend/app/tools/`、`backend/app/services/cart_service.py` | 加购、删除、修改数量、查看、结算 |
| 多模态 | `backend/app/multimodal/` | 图片理解、视觉查询构造、图文融合检索 |
| 进度事件 | `backend/app/progress/` | 快速 progress 文案和调试记录 |

## 2 相比最初版本的新增能力

1. Doubao-first IntentPlan：复杂、多动作、模糊表达优先让 Doubao 拆成系统可执行动作序列。
2. Grounded RAG：Doubao 只能基于后端传入的真实商品候选生成回复，不直接编造商品。
3. 事件记忆：稳定记录“第一款/第二个/刚才那个”对应的商品，支持详情、对比、购物车回溯。
4. 统一前端输出：每轮最终统一为 `frontend_events`、`frontend_data`、`system_debug`。
5. progress events：请求进入后先流式输出等待提示，前端不会空白等待 Doubao。
6. 商品增强字段：商品亮点、适用场景、人群标签、非标准问题标签参与召回、重排和推荐理由。
7. 层次化个性化：用户历史、领域风格、协同过滤、隐私模式共同影响回复。
8. 购物车侧个性化：购物车中同类商品会作为软约束影响新推荐排序和解释重点。
9. 多模态图文融合：支持 JSON 图片路径和 multipart 图片上传。
10. 鲁棒 fallback：严格无结果时逐步放宽预算、子类目等约束，给真实相近备选。
11. 智能下单闭环：用户加购后按购物车件数温和引导结算；用户拒绝后进入冷却。
12. 耗时统计：`system_debug` 中记录模块耗时、模型调用次数、最慢模块等。

## 4. 前端怎样读取输出

主对话接口是 SSE。前端会陆续收到：

```text
event: progress
event: state
event: token
event: product_cards / products / alternatives / cart / product_detail
event: frontend_action
event: turn_result
event: done
```

前端最重要的是最终 `turn_result`。它包含三大块：

```json
{
  "frontend_events": [],
  "frontend_data": {},
  "system_debug": {}
}
```

### 4.1 frontend_events

这是前端动作列表，按顺序执行。示例：

```json
[
  {
    "步骤": 1,
    "动作类型": "show_reply",
    "含义": "展示系统回复",
    "数据参考": "reply_message",
    "blocking": false
  },
  {
    "步骤": 2,
    "动作类型": "show_products",
    "含义": "展示推荐商品卡片或商品图片",
    "数据参考": "recommended_products",
    "blocking": false
  }
]
```

常见动作类型：

| 动作类型 | 前端动作 | 常见 data_ref |
|---|---|---|
| `show_reply` | 展示 AI 回复文本 | `reply_message` |
| `show_products` | 展示商品卡片 | `recommended_products` / `alternative_products` |
| `show_product_detail` | 展示商品详情 | `product_detail` |
| `update_cart` | 更新购物车角标/购物车页面 | `cart_state` |
| `navigate` | 页面跳转 | `navigation` |
| `update_page_state` | 更新筛选条件、当前类目等非对话状态 | `page_state` |
| `show_clarification_options` | 展示澄清选项 | `clarification_options` |
| `show_error` | 展示错误提示 | `error_message` |

重要原则：只有出现 `navigate` 时才跳转页面。其他情况默认留在聊天页。

### 4.2 frontend_data

这里存放 `frontend_events` 里 `数据参考` 对应的数据。前端按 `frontend_events` 顺序取值即可。

常见字段：

| 字段 | 用途 |
|---|---|
| `reply_message.text` | 展示给用户的 AI 回复 |
| `recommended_products.products` | 推荐商品卡片 |
| `alternative_products.products` | 相近备选商品卡片 |
| `product_detail.product` | 商品详情页数据 |
| `cart_state.cart` | 购物车和订单数据 |
| `navigation.target_page` | 跳转目标页面 |
| `page_state.cart_badge_count` | 购物车角标数量 |

商品卡字段都来自真实商品库，前端可以放心展示名称、价格、图片、推荐理由。

### 4.3 system_debug

这是系统调试信息，不给普通用户展示。它用于验收和排查：

- 本轮理解：意图、流程、类目、约束；
- RAG 检索过程：召回数量、最终推荐 SKU、评分；
- 工具执行：购物车工具是否成功；
- 模型调用：Doubao 是否真实调用、调用目的、耗时；
- 运行耗时统计：总耗时、最慢模块；
- progress 调试：首条 progress 耗时、输出条数；
- 个性化、隐私、多模态、商品增强字段命中情况。

## 5. progress_events 等待提示

progress events 是前端等待态文案，不是模型推理链。请求刚进入后端时就会启动，正常应早于 Doubao/RAG 结果返回。

前端处理建议：

1. 收到第一个 `progress` 时显示“正在处理”的 loading 区域；
2. 后续 progress 文案可以替换上一条，也可以按时间轴展示；
3. 一旦收到正式 `turn_result` 或 `done`，停止 progress，展示正式结果；
4. 使用 curl 测试时必须加 `-N`，否则看不到实时流式效果。

示例 progress：

```text
正在理解您的需求
正在提取关键条件
正在商品库中查找
正在筛选更合适的商品
正在组织回复
```

如果是老用户或购物车非空，会出现类似：

```text
正在结合您的历史偏好筛选商品
正在参考购物车中的相关商品
```

## 9. 前端接入重点

1. 前端只按 `frontend_events` 顺序执行动作。
2. 每个动作从 `frontend_data` 读取 `数据参考` 对应字段。
3. 不要把 `system_debug` 展示给普通用户。
4. 只有 `frontend_events` 中出现 `navigate` 才跳转页面。
5. `show_products` 和 `show_product_detail` 都可能展示商品，前者是列表，后者是单个详情。
6. `alternative_products` 不是错误，是无 exact match 时的真实备选。
7. 购物车状态以 `cart_state.cart` 为准，不要从回复文本里解析价格或数量。
8. progress 是等待提示，最终 UI 以 `turn_result` 为准。
9. 商品事实以商品卡片为准，回复文案只是导购解释。
10. 如果 curl 看不到流式 progress，确认用了 `curl -N`。

## 10. 常见问题

### 10.1 为什么有时等 20-60 秒？

主要是远程 Doubao API 耗时。复杂轮次通常会调用 1-2 次 Doubao：一次意图计划，一次回复生成。请看 `system_debug.运行耗时统计` 判断具体慢在哪里。

### 10.2 为什么 TestClient 看不到即时 progress？

FastAPI TestClient 会缓冲流式响应，不适合验证首条 progress 到达时间。请用 `curl -N` 或 `scripts/http_stream_observer.py`。

### 10.3 商品结果看起来不是 exact match 怎么办？

先看 `frontend_data` 是 `recommended_products` 还是 `alternative_products`。如果是 `alternative_products`，说明后端没有完全命中库存，正在提供真实相近备选。

### 10.4 前端应该跳到商品详情页吗？

只有 `frontend_events` 里出现 `navigate`，且 `navigation.target_page = product_detail_page` 时跳转。否则就留在聊天页展示卡片。

### 10.5 用户历史没有恢复怎么办？

确认请求里有：

```json
"metadata": {
  "resume_session_id": "xxx"
}
```

当前后端会自动把 `resume_session_id` 视为恢复请求，不需要额外传 `resume=true`。

### 10.6 图片上传失败怎么办？

检查：

1. 图片小于 8MB；
2. 表单字段名是 `image`；
3. `input_type=image_text`；
4. 服务端 `.env` 使用真实 Doubao；
5. `system_debug.多模态分析` 是否有视觉结果或 fallback 结果。

## 11. 交接建议

前端联调优先跑这四类：

1. 普通商品推荐：验证商品卡片展示；
2. 老用户恢复：验证个性化和历史恢复；
3. 购物车操作：验证 update_cart 和 navigate；
4. 图片上传：验证 multipart 和多模态商品匹配。

调试时先看最终 `turn_result`，再看 `system_debug`。如果用户回复文本和商品卡片冲突，以商品卡片和商品库事实为准，并反馈后端继续优化 prompt 或防幻觉校验。
