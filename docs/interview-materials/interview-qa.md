# 面试问答准备

基于已确认的项目事实，为 AI Agent 工程师面试准备的问答材料。

1. 意图理解 → 三阶架构（严格模板->LLM结构化解析->本地规则降级）

  设计哲学： 不判断"难度"，只拦截"确定性"。

  面试回答： 业界常见做法是阈值路由——让 LLM判断置信度，高于阈值走大模型、低于阈值走规则。但我发现这个方案有个根本缺陷：你凭什么相信 LLM的判断？把复杂查询误判为简单查询的代价远大于反过来。所以我换了思路。第一阶严格模板匹配，只用正则拦截 100%无歧义的查询——"推荐一款防晒"能抓到，"推荐一款不太油的适合夏天用的防晒"立刻放行。不追求拦截率，追求零误杀。第二阶 LLM是默认路径，所有有歧义的查询直接走 Doubao，输出包含 25 个字段的结构化 IntentPlan。第三阶规则回退只在 LLM挂掉时触发——这是安全网，不是降级方案。和阈值路由的本质区别：我没有用一个不可靠的判断来决定流量的走向。

```
第一层：严格模板 _parse_strict_template

只处理非常简单、风险较低的句式，例如：
推荐一款跑鞋
想要一个背包
选择一款防晒
预算500元
一旦包含以下复杂信息，就不会走本地模板：
否定：“不要、排除、拒绝”
上下文：“刚才、之前、这款”
购物车：“加购、删除、结算”
比较：“哪个、哪款、对比”
多动作：“然后、同时、顺便”
场景组合：“一套、清单、方案”
这样设计的目的，是避免简单正则错误处理复杂语义。

第二层：豆包 _parse_with_llm
只要没有命中严格模板，就调用：
self.llm_client.resolve_user_intent(...)
发送给豆包的上下文比较完整，包括：
当前用户消息。
系统支持的全部意图。
商品库实际存在的大类和子类。
当前对话类目和约束。
最近推荐的商品。
当前购物车商品。
一系列意图判断规则。
豆包返回结构化 JSON 后，再由：
_parsed_query_from_llm_payload()
进行二次校验和修正。
这一步不是完全相信大模型，而是使用本地规则纠正它，例如：
豆包把单个“背包”误判为场景搭配，会被改回推荐。
豆包把普通追问误判为比较，但用户没有真实比较词，会被改回推荐或追选。
豆包返回不存在的商品类目时，会根据商品库进行归一化。
本地重新提取价格、品牌和否定条件，补充豆包漏掉的字段。
结合上一轮状态判断是否继承上下文。

第三层：规则降级 _parse_legacy_rule
当豆包不可用或返回无效结果时，模块会降级到：
关键词规则识别意图。
text2vec 小模型修正意图。
规则提取价格、类目、品牌和属性。
根据对话状态锁定当前主题。
构造简单的 IntentPlan。

因此系统即使没有大模型，也不会直接崩溃。
```

  2. 混合检索 → 5 阶段管线

  设计哲学： 硬过滤删掉"绝对不行"的，软打分排出"谁更好"，模型重排序做精细化调整。

  面试回答：检索我用了 5 阶段管线，分成"删"和"排"两步。 "删"的是硬过滤——类别不匹配、价格超预算、品牌被用户明确排除、涉及儿童安全风险的（比如给儿童推咖啡因饮料）。这一层是规则驱动的，宁可多删不少删。"排"的是七维轻量打分——关键词匹配、语义相似度（字符 bigram Jaccard）、约束满足度、商品标签增强、品牌偏好、价格适配度、差评标记。每个维度独立计算，然后加权融合。有 Reranker的时候加入 BGE-reranker-base 的交叉编码打分，占 10% 权重。

为什么不用纯向量检索？因为电商场景中硬约束是二值的——"200元以内"不满足就是不满足，用向量相似度压不过去。混合检索本质上是在硬约束的可行域内做软排序。

硬过滤在 `_hard_filter()` 中实现，按优先级依次检查：类目不匹配 → `category_mismatch`，子类目不匹配 → `sub_category_mismatch`，价格越界 → `price_above_max`/`price_below_min`，品牌不在包含列表 → `brand_not_included`，品牌在排除列表 → `brand_excluded`，否定约束词命中且无"安全词"（如"不含酒精"）→ `negative_constraint`。安全词判断是关键设计：如果用户要求"不要酒精"，而商品描述中明确写了"不含酒精"，该商品不会被误排，因为 `_negative_satisfied_by_safe_word()` 识别"不含酒精"为安全词。

多维评分中，每个商品独立计算七个维度分。关键词分（`_keyword_score`）和字符 n-gram 语义分（`_semantic_score`）无需模型即可计算，保证最低可用性。语义向量分（`LocalModelManager.semantic_scores`）和重排序分（`LocalModelManager.rerank_scores`）在有模型时补充更精确的信号。约束分（`_constraint_score`）检查正向约束词在商品文本中的命中率。增强分（`_enhancement_score`）利用商品的结构化标签（适用场景、目标用户、非标准查询标签）进行语义增强匹配，弥补纯文本检索对长尾表达的覆盖不足。偏好分（`_preference_score`）根据用户长期画像加减分。价格适配分（`_price_fit_score`）计算商品价格与预算的比例适配度。

加权融合：有 reranker 时 `final = 0.18×kw + 0.24×sem + 0.22×constraint + 0.08×enhancement + 0.10×price_fit + 0.08×pref + 0.10×reranker`，无 reranker 时 `final = 0.24×kw + 0.28×sem + 0.22×constraint + 0.12×enhancement + 0.10×price_fit + 0.04×pref`。外加类目精准匹配 +0.15、子类目精准匹配 +0.18、品牌匹配 +0.08。

对于对比、详情、商品问答等需要锁定特定商品的场景，系统使用 `retrieve_by_references()` 替代全库检索——从 session state 的指代映射、最近推荐事件和购物车中定位目标商品，避免不必要的全库扫描。

  3. 记忆系统 → 三层架构

设计哲学： 会话记忆做即时响应，事件记忆做指代锚定，历史记忆做长期积累。三层分工，每层解决不同时间尺度的问题。

面试回答：多轮对话 Agent 最大的挑战不是"生成一句话"，而是"知道用户在说什么"。用户说"第一个太贵了，有没有便宜一点的"——Agent必须知道"第一个"是什么。这需要记忆。我设计了三层记忆。最底层是会话记忆 SessionMemory，管理当前对话状态——17种对话流追踪、当前类别锁定、话题切换检测。用户从"推荐防晒"聊到"看看购物车"，Agent 需要知道上下文切了。

中间层是事件记忆。每次推荐、对比、加购都记录为结构化事件。推荐事件包含 rank→SKU 映射和 8个中文别名——"第一个""第一款""1 号"——确保无论用户怎么说都能定位。还有代词绑定："这个""它""刚才加购的"都指向具体的SKU。事件链通过 source_event_id 追踪——你可以追溯"这个推荐是从哪轮对话产生的"。

最上层是用户历史，持久化到文件系统。每轮保存完整 turn 记录和状态快照，支持服务重启恢复。语义记忆category_counts、feature_counts、brand_counts 计数器——这是个性化系统的数据基础，不需要LLM重新总结就能知道"这个用户偏爱什么品牌、什么价位"。



第一层是短期会话状态记忆，核心是 SessionState。它维护当前意图、商品类目、活跃筛选条件、缺失槽位、最近推荐结果和购物车状态，主要解决上下文省略和话题延续问题。比如用户先说“推荐几款500元以内的跑鞋”，下一轮只说“再轻一点”，系统会继承跑鞋类目和原有预算，再增加轻量条件；但如果用户明确改成“推荐一个手机”，系统会判断发生话题切换，不再继承跑鞋的价格、品牌和特征约束。

第二层是结构化事件记忆。推荐、详情、比较和购物车操作在真正执行成功后，才会写成事件，而不是意图识别后就提前记录。推荐事件会保存 rank 到 SKU 的映射，并提前生成“第一个”“第一款”“第1个”“1号”等别名，因此用户说“把第二款加入购物车”时，可以直接通过字典定位到具体 SKU。对于“这个”和“它”，系统优先指向刚查看过详情的商品，否则指向最近推荐的第一款；“刚才加购的”则通过 active_cart_sku_id 定位。详情、比较和加购事件还通过 source_event_id 关联到来源推荐事件，支持行为溯源。

第三层是长期用户记忆，跨会话持久化到文件系统。它内部包含两部分：一部分是完整的 turn 历史和 SessionState 状态快照，用于服务重启后的会话恢复；另一部分是 semantic_memory，也就是从历史交互中累计出的类目、特征、品牌、价格、加购和购买等计数画像。这些长期偏好主要用于后续推荐的软排序和画像提示，不会覆盖用户当前明确提出的要求。

  4. 个性化 → 5 层机制 + 协同过滤

  设计哲学： 个性化不是"给推荐结果加个标签"，而是嵌入检索和推荐的每一个环节——从过滤到排序到文案生成。

面试回答：个性化我放了五层，按影响深度从硬到软。第一层硬约束——用户明确不喜欢的品牌、过敏成分，在检索阶段直接过滤。第二层用户画像——两种生成模式：正常模式走 LLM 摘要，隐私模式走纯语义统计（只存计数不存原文）。第三层购物车感知——40 多条配对规则，购物车里有 MacBook就提升苹果配件权重，有洁面+化妆水就提示护肤流程缺面霜。这不是"买了还推荐"的协同过滤，而是基于品类生态的互补推荐。第四层领域导购风格——美妆是细腻的小姐姐、数码是理性的小哥，不同品类用不同的推荐语气。第五层隐私控制——full/semantic/off 三档，semantic 模式只存统计量不存原始对话。协同过滤是跨用户的部分。我把当前用户的画像、偏好、近期历史拼成一份"风格文档"，和参考用户库做 BGE embedding语义匹配。融合公式是 max(语义相似度, 词汇相似度×0.88)×0.72 + 类别重合度×0.28。阈值0.38，语义优先、词汇回退、品类做硬校验。设计目标是"宁可少召回也不引入噪声"。

---
  5. 幻觉防控 → 事前隔离 + 事后校验

  设计哲学： 防幻觉最有效的方法是限制 LLM 能看见什么，不是检查它说了什么。

  面试回答：幻觉防控我做了两层，分别在 LLM 的入口和出口。入口——事实隔离。LLM 不是看到整个商品库 151 件商品，而是只看到检索管线筛选出的候选商品（3-5件）的验证事实。这就从根本上缩小了"说谎空间"——LLM 可以推荐的都在候选集里，它编不出不存在的东西。
 出口——ResponseValidator。产品名校验：提取 LLM 输出中的所有已知商品名，如果出现候选集之外的 → 触发回退。价格校验：提取¥{数字} 模式，排除预算上下文（"以内""不超过"等 8 个豁免词），比对候选商品真实价格集合。触发回退时不重试 LLM——直接走安全模板，用排名第一的候选商品生成回复。为什么？因为 LLM第一次已经产生了幻觉，再试一次大概率还是幻觉。工程上不赌概率。

---
  6. 工具调用 → 自然语言购物车 + 8 级 SKU 解析

  设计哲学： Agent 的工具调用不是"把 API 包装成 function call"，而是处理自然语言的模糊性——用户不说 SKU
  编号，说"把刚才那个便宜一点的加入购物车"。

  面试回答：购物车操作的难点不在 CRUD，在于把自然语言映射到具体的 SKU。我设计了 8 级 SKU 解析优先级链。最优先的是价格选取——用户说"最便宜的那个"直接定位。然后是 LLM intent_plan 中的cart_action 字段、记忆事件引用匹配（"刚才那个"）、查询文本中出现的关键词与购物车内商品的语义匹配。最后兜底：购物车唯一商品或最新推荐的首个商品。多 SKU 商品——比如同一个防晒有 30ml 和 50ml 两种规格——加购时必须选规格。ActionExecutor 检测到多 SKU会拒绝加购并触发规格选择器 SSE 事件，前端弹出选择 UI。这保证用户不会不小心买了不想买的规格。批量操作也支持——"把这两个都加入购物车""删除购物车里的所有防晒"——系统识别"都""所有""全部"等批量信号，一次执行多个操作。

---
  7. 流式输出 → 20+ SSE 事件类型 + 推荐流式协议

  设计哲学： SSE 事件类型不是越多越好——每种事件对应一种前端 UI
  状态变更。事件设计的原则是"后端告诉前端发生了什么，前端决定怎么展示"。

  面试回答：流式输出我用 SSE 协议，设计了 20 多种事件类型。分成四类：进度类（告诉用户系统在干什么）、内容类（推荐文案逐 token 或逐section 展示）、数据类（商品卡片、购物车快照、规格选择器）、控制类（页面导航指令、流结束信号）。最值得讲的是推荐流式协议。LLM 可能会一次推荐 3-5 个商品，如果等全部生成完再展示，用户会等很久。我设计了一个 SECTION标记协议——LLM 输出中插入 [[SECTION:1]]...[[END_SECTION]] 标记——后端流式发出，前端增量解析。即使 token边界刚好切在标记中间，解析器也能正确恢复。前端打字机效果根据状态动态调整步长和延迟——已完成段落快速回放（6-8 字符/步），流式段落慢速跟随（2-6字符/步），去重检测防止重复展示。进度事件独立于 LLM 生成——每 700ms交错发送进度更新（"正在理解你的需求→正在筛选商品→正在生成推荐"），用户不会面对一个空白页面干等。

---
  8. 对话流控制 → 17 种流程 + 优先级链

  设计哲学： Agent 的对话不是"意图→回复"的一对一映射，而是要在 17 种可能的流程中选一个，同时支持中途切换。

  面试回答：Agent 收到一条消息后，不只是判断意图然后生成回复。我设计了一个对话流决策层——DialogueFlowController——在意图识别之后、生成回复之前，决定"这一轮对话应该走哪条流程"。17 种流程——问候、推荐、筛选、细化、澄清、对比、商品问答、场景捆绑、购物车操作、结账、偏好更新、无结果、闲聊、越界、无效、详情、结账引导。

决策逻辑是一个优先级链：先判断是否无效或越界 → 是否有购物车操作和结账信号 → 是否在更新偏好 → 是否为闲聊 →是否在对比或看详情 → 是否需要场景捆绑 → 是否需要澄清 → 是否有排除条件 → 是否为筛选或细化 → 默认走推荐。

话题切换是这里面最复杂的。用户可能在推荐中说"等一下，购物车里有什么？"——系统需要判断这是话题切换还是延续。我通过_should_lock_current_topic() 和 _message_suggests_topic_switch()两个函数来判断，前者检测延续信号（"有便宜一点的吗"），后者检测跨类目信号（"看看数码产品"）。

---
  9. 异常降级 → LLM 三层降级 + 全流程异常捕获

  设计哲学： 降级不是"出错了再说"，而是要预先设计好每一层的降级路径和用户感知。

  面试回答：系统有三层降级。LLM 降级：Doubao API（真实）→ MockLLMClient（本地规则引擎，200+ 行意图解析+模板回复）→ 硬编码文案。MockLLMClient不是简单返回"系统繁忙"——它有完整的意图解析逻辑和模板回复，甚至模拟了流式输出（17字符分块），让用户在降级模式下仍然能正常对话。检索降级：S004 的4级渐进松弛。每次松弛记录做了什么、为什么，并在回复中告知用户——"我适当放宽了价格范围"——透明度不丢失。全局异常捕获：整个 _stream_chat_core() 被 try/except 包裹。任何未捕获的异常不会让流断裂——而是依次发出turn_result（含错误信息）、error 事件、done 事件。前端收到 error事件后展示"系统暂时遇到了问题，请重试"，后端保留完整的 system_debug 信息用于排查。
设计原则：不管内部出了什么问题，用户侧的体验是受控的——要么正常响应，要么优雅降级，要么明确告知"出了问题"，但永远不会是空白页或断开连接。

---
  10. 多模态 → 图片搜索管线

  设计哲学： 用户上传一张图片说"我想找类似风格的"，这不是纯 CV 任务——需要 VLM 理解 + 文本检索融合。

  面试回答：图片搜索我做了端到端管线。用户上传图片 → VisionAnalyzer 调 Doubao VLM 分析视觉属性（颜色、风格、品类）→VisualQueryBuilder 把视觉属性融合到文本查询中 → VisualProductMatcher 做图片到商品的匹配。匹配分三策略：fixture匹配（商品图直接对比）、别名匹配（视觉描述中的品类名映射到商品类别）、特征相似度（颜色/风格向量匹配）。如果 VLM不可用，降级到关键词匹配（confidence 约 0.48），虽然弱但不阻断流程。这个模块的当前限制是 Doubao 视觉模型的能力有限——复杂场景的理解不如 GPT-4V——但我设计的管线是模型无关的，换 VLM只需要替换 VisionAnalyzer 的实现。

## 一、项目介绍题

### Q1: 请简单介绍你的项目

**建议回答框架**：
> 我构建了一个 RAG 多轮电商导购 AI Agent 系统。用户可以用自然语言描述需求（如"帮我推荐适合混油皮的清爽防晒，预算 300 以内"），系统理解意图后从真实商品库检索、打分、排序，通过 LLM 生成有理由的推荐，并通过 SSE 流式返回给 Android 客户端。系统还支持多轮对话、个性化记忆、自然语言购物车操作、图片搜索和结账引导。

**关键数字**：
- 151 件真实商品，4 大类，美妆 24 个子类目
- 18 种意图类型，17 种对话流
- 后端 50+ Python 文件，前端 37 个 Kotlin 文件
- 20+ SSE 事件类型
- 3 个本地 ML 模型

### Q2: 这个项目解决的核心问题是什么？

1. **搜索效率**：用户不需要自己从大量商品中筛选，Agent 理解复杂需求并直接给出推荐
2. **推荐可信度**：基于真实商品库 + 事实边界隔离 + 输出校验，防止 LLM 编造
3. **个性化**：记住用户偏好，千人千面的导购体验
4. **转化闭环**：推荐→比较→加购→结账，一站式完成

## 二、架构设计题

### Q3: 为什么选择三阶意图理解（模板→LLM→规则）而不是直接用 LLM？

**技术原因**：
1. **延迟**：简单查询（如"推荐一款精华"）可以通过模板在 <1ms 内完成，不需要等待 LLM ~2s
2. **可靠性**：LLM 输出可能无法解析为 JSON，规则回退作为保底方案保证系统可用
3. **成本**：减少不必要的 LLM 调用（问候、越界输入等）
4. **可控性**：模板匹配对简单模式更精确

**代码证据**：`backend/app/agents/query_understanding.py` — `parse()` 方法

### Q4: 为什么 SSE 事件要设计 20+ 种而不是简单的"一次性返回所有结果"？

1. **用户体验**：即时反馈（进度事件），减少感知等待
2. **流式展示**：推荐理由逐字显示（打字机效果），更像真人在导购
3. **前端解耦**：progress → token → recommendation_section → product_card 各有独立的 UI 组件
4. **可中断**：用户可以在流式输出过程中继续输入

**代码证据**：`backend/app/utils/sse.py` + `ChatViewModel.kt` — `handleStreamEvent()`

### Q5: 为什么 Agent 不使用 LangChain/AutoGPT 等框架，而是自建编排？

**代码证据表明的设计选择**：
1. **可控性**：ShoppingAgent 的 10 阶段编排完全是确定性的代码逻辑，不存在 Agent 框架的黑盒行为
2. **性能**：LangChain 的 Agent 循环模式（thought→action→observation→thought...）会显著增加 LLM 调用次数
3. **领域适配**：电商导购有明确的业务流程（17 种），不需要通用的 ReAct 循环
4. **依赖最小化**：requirements.txt 仅 7 个依赖，无框架锁定

### Q6: 混合检索的 7 维权重是如何设计的？

- **有 Reranker 时**：keyword 0.18, semantic 0.24, constraint 0.22, enhancement 0.08, price_fit 0.10, preference 0.08, reranker 0.10
- **无 Reranker 时**：keyword 0.24, semantic 0.28, constraint 0.22, enhancement 0.12, price_fit 0.10, preference 0.04

**设计思路**（合理推断）：
- Semantic 权重最高（语义匹配是核心）
- Reranker 存在时分担了 semantic 的部分权重
- Preference 权重较低（避免个性化过强覆盖用户当前需求）

**代码证据**：`backend/app/retrieval/hybrid_retriever.py` — `retrieve()` 方法

## 三、Agent 技术题

### Q7: Agent 的状态管理是怎么做的？

**三层状态管理**：

| 层 | 存储 | 生命周期 | 内容 |
|----|------|---------|------|
| 会话状态 | SessionMemory (内存 dict) | 服务重启丢失 | 对话状态、事件记忆、引用图谱 |
| 事件记忆 | 会话状态的一部分 | 会话内 | RecommendationEvent, CartEvent 等（最近 20 条） |
| 用户历史 | UserHistoryStore (文件系统 JSON) | 持久化 | Profile, SemanticMemory, MemoryCards |

**关键设计**：
- 会话状态通过 state_snapshot 序列化到文件系统，支持恢复
- 事件记忆包含 rank_to_sku 映射，支持"第一个"这类指代消解
- 语义记忆通过 `_promote_turn_memory()` 在每轮后增量更新

**代码证据**：`backend/app/memory/session_memory.py` + `user_history_store.py`

### Q8: 如何处理多轮对话中的上下文继承？

1. **话题锁定**：`_should_lock_current_topic()` 检测是否延续上一轮话题
2. **约束合并**：`context_merge` 将当前轮次的约束与历史约束合并
3. **指代消解**：8 个别名/排名 + 代词绑定 + 事件链追踪
4. **意图继承**：REFINE/FILTER 意图自动继承上一轮类别

**代码证据**：`shopping_agent.py` — `_stream_chat_core()` 阶段 3

### Q9: 系统的容错和降级策略是什么？

1. **检索容错**：4 级渐进式松弛（价格→子类目→否定→全库存）
2. **LLM 降级**：DoubaoClient → MockLLMClient（200+ 行规则引擎）→ 模板回复
3. **意图理解降级**：LLM IntentPlan → 规则回退（200+ 条别名）
4. **画像生成降级**：LLM → 语义计数器 → 关键词回退
5. **视觉分析降级**：VLM → 关键词匹配回退
6. **全局异常捕获**：try/except 整轮 → 格式化的错误 SSE 事件序列

### Q10: 如何防止 LLM 幻觉？

1. **事前隔离**：LLM 只能看到 `Verified product facts`（当前候选商品），无法看到全库存
2. **事后校验**：ResponseValidator 扫描输出中的产品名和价格
3. **价格上下文豁免**：8 个预算相关 token（"以内"、"以下"、"预算"、"不超过" 等）不会被误判
4. **安全回退**：检测到幻觉时用排名第一的真实商品生成安全文案

**代码证据**：`backend/app/agents/response_validator.py`

## 四、RAG 与 Memory 题

### Q11: 你的 RAG 和标准 RAG 有什么区别？

**标准 RAG**：Embedding → 向量检索 → Top-K → LLM 生成

**本项目的 RAG**：
1. **意图理解前置**：先解析意图（类别、约束、价格），再检索
2. **硬过滤优先**：在语义匹配之前用业务规则排除不相关商品
3. **七维混合打分**：不仅看语义相似度，还考虑约束满足、偏好、价格适配
4. **查询扩展**：`_enhanced_query()` 将领域同义词加入检索（如 "皮肤干" → "皮肤干燥起皮 补水保湿推荐 干皮"）
5. **后处理校验**：否定词安全处理，去除未通过硬过滤的商品
6. **渐进式容错**：0 结果时自动松弛约束

**代码证据**：`backend/app/retrieval/hybrid_retriever.py`

### Q12: 用户记忆如何跨会话持久化？

1. **存储格式**：`storage/user_history/{user_id}/profile.json` + `sessions/{session_id}.json`
2. **每轮持久化**：`UserHistoryStore.save_turn()` 在每轮对话后写入磁盘
3. **语义积累**：`_promote_turn_memory()` 增量更新类别计数、特征计数、品牌计数等
4. **画像更新**：`UserProfileService.maybe_refresh_profile()` 非强制模式下按需更新（LLM 调用）
5. **记忆卡片**：每个偏好/行为被提升为记忆卡片（confidence × last_seen_at 排序），保留前 50 条

**代码证据**：`backend/app/memory/user_history_store.py`

### Q13: 协同过滤具体怎么实现的？

1. 构建"风格文档"（画像 + 最近轮次 + 当前查询）
2. 从优先级列表 + 全局用户池加载候选参考用户
3. `LocalModelManager.semantic_scores()` 计算当前用户与候选用户的语义相似度
4. `_lexical_similarity()` 作为词汇级回退
5. 类别重叠得分
6. 融合：`max(语义, 回退×0.88) × 0.72 + 类别重叠 × 0.28`
7. 阈值 0.38（有语义分）或 0.28（无语义分）
8. Top 3 相似用户的 profile 和 few-shot 示例注入 prompt

**代码证据**：`backend/app/memory/personalization_service.py` — `_collaborative_style_reference()`

## 五、工程化题

### Q14: 你的依赖注入是怎么设计的？

- 使用 `@lru_cache` + 工厂函数模式（非装饰器 DI 框架）
- 所有依赖在 `backend/app/core/dependencies.py` 中集中管理
- `ShoppingAgent` 接收 20 个依赖参数
- 优势：零外部依赖、类型安全、易于测试（可替换任何依赖）
- 劣势：手动管理依赖图，新增模块需要修改工厂函数

**代码证据**：`backend/app/core/dependencies.py`

### Q15: 如何处理 LLM 调用的超时和重试？

- `generate_response()`：超时 20s
- `stream_generate_response()`：超时 30s
- `decide_frontend_action()`：超时 25s，重试 2 次
- `resolve_user_intent()`：超时 25s，重试 2 次
- `analyze_user_profile()`：超时 18s，重试 1 次
- JSON 提取失败时自动尝试截取 `{...}` 重新解析
- 全部失败时触发对应的回退路径

**代码证据**：`backend/app/llm/doubao_client.py` — 各方法的 timeout 参数

### Q16: 有没有做 A/B 测试或效果评估？

**代码证据**：`测试场景与测试用例.md` — TC-PRIV-001; `docs/综合测试报告cc.md:254-263`

## 六、项目难点题

### Q17: 这个项目最大的技术挑战是什么？

**候选回答（需要根据你的实际经历选择/调整）**：

1. **LLM 输出的可控性**：如何让 LLM 既保持自然语言的表现力，又不编造商品信息？
2. **多轮对话的上下文管理**：如何在有限 token 内传递足够的对话历史和个性化信息？
3. **实时流式 + 复杂 UI 的协调**：20+ SSE 事件类型如何在 Android 上正确组装为连贯的 UI？
4. **意图理解的工程权衡**：如何在延迟（<1ms 模板）和准确率（~2s LLM）之间取得平衡？

### Q18: 遇到过一个具体 bug 是怎么解决的？

以下是从代码中观察到的设计迭代线索：

1. **InputPreprocessor 的"好的"误判**（`input_preprocessor.py`）："拍照好的手机"中的"好的"曾被误判为问候。解决方法：添加产品意图词检测，在 `_is_greeting()` 中检查是否为产品相关短语。

2. **ResponseValidator 的价格误判**（`response_validator.py`）：LLM 说"在 300 元以内"时，"300 元"被误判为幻觉价格。解决方法：添加 8 个预算上下文 token 豁免。

3. **Windows 文件名乱码**（`product_repository.py`）：商品图片在 Windows 文件系统上的路径包含 mojibake 字符。解决方法：rglob 文件名匹配回退。

### Q19: 这个系统和 ChatGPT 插件/Copilot 有什么不同？

1. **领域深度**：ChatGPT 是通用对话，本系统有领域特定的意图类型（18 种）和业务流程（17 种）
2. **可信度机制**：事实边界隔离 + 双重验证，而 ChatGPT 插件可能返回不存在的信息
3. **个性化**：5 层个性化（硬约束→画像→购物车→风格→隐私），而非通用的 memory 功能
4. **业务闭环**：推荐→加购→结账是完整的电商转化链路，而非独立的问题回答
5. **成本优化**：本地模型（embedding/reranker）+ 模板路由减少不必要的 LLM 调用

## 八、压力追问题

### Q22: 如果商品库扩大到 10 万件，你的检索方案需要怎么改？

1. **Embedding 预计算 + 向量数据库**：当前方案每次检索时对所有商品计算 embedding，需要改为预计算 + Milvus/Qdrant
2. **两阶段检索**：粗排（向量检索 Top-100）→ 精排（混合打分 + Reranker Top-10）
3. **硬过滤前置**：在向量检索前就通过类别/价格索引过滤
4. **分片策略**：按类目分片，减少单次检索范围

### Q23: 如果 Doubao API 完全不可用，你的系统还能工作吗？

**能**，代码中已有完整降级：
1. MockLLMClient 替代 LLM（200+ 行规则意图解析 + 模板回复）
2. 本地 embedding/reranker 模型（BGE + text2vec）替代 API 的语义能力
3. 模板回复覆盖所有核心流程（推荐、购物车、结账、问候等）
4. 规则意图解析覆盖 16 种意图 + 200+ 条类别别名

**但降级后的局限**：
- 回复模板化，缺乏个性化表达
- 复杂场景（场景捆绑、商品对比）质量下降
- 多模态功能完全不可用

### Q24: 系统的延迟瓶颈在哪里？

**代码中可观察到的耗时点**：
1. Doubao LLM IntentPlan 调用（~2s）
2. Doubao LLM 回复生成（~3-5s）
3. 本地模型推理：embedding + reranker（~0.5-2s，取决于 CPU 和商品数量）
4. 图片分析 VLM 调用（~3s）
5. 画像刷新 LLM 调用（非每轮触发）

**优化方向**（合理推断）：
- LLM 调用并行化（IntentPlan 和回复生成无法并行，但图片分析和意图理解可以）
- Embedding 预计算和缓存
- 流式输出减少感知延迟（已实现）
- 进度事件提供即时反馈（已实现）

### Q25: 如果你现在重写这个系统，会怎么设计？

可能的改进方向（需要你根据实际反思回答）：
1. 使用向量数据库替代内存检索
2. 引入 Agent 评测框架和自动化回归测试
3. 前端改用声明式 SSE 解析（Kotlin Flow + sealed class 事件层次）
4. 购物车状态迁移到 Redis 实现服务无状态
5. 添加 LLM 调用缓存减少重复调用
6. 引入结构化日志和分布式追踪

## 九、项目不足和改进方向

### Q26: 你认为这个项目最大的不足是什么？

**可以从代码中确认的不足**（避免显得在自我批评）：
1. 商品库规模小（151 件），大规模下的检索效果未验证
2. 测试覆盖不足（前端零测试，后端仅基础 API 测试）
3. 单机架构，无法水平扩展
4. 用户画像完全依赖对话历史，无外部信号（浏览、点击、购买）
5. LLM 输出的风格一致性没有 A/B 测试验证

### Q27: 如果有更多时间，你会优先做什么？

建议优先级：
1. P0：补充核心流程的集成测试和回归测试套件
2. P0：LLM 调用的可观测性（延迟、成功率、token 用量）
3. P1：检索性能优化（embedding 预计算、向量数据库）
4. P1：商品库扩容 + 大规模下的效果验证
5. P2：前端单元测试
6. P2：多语言支持
