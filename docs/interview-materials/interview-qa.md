# 面试问答准备

  6. 工具调用 → 自然语言购物车 + 8 级 SKU 解析

  设计哲学： Agent 的工具调用不是"把 API 包装成 function call"，而是处理自然语言的模糊性——用户不说 SKU
  编号，说"把刚才那个便宜一点的加入购物车"。

  面试回答：购物车操作的难点不在 CRUD，在于把自然语言映射到具体的 SKU。我设计了 8 级 SKU 解析优先级链。最优先的是价格选取——用户说"最便宜的那个"直接定位。然后是 LLM intent_plan 中的cart_action 字段、记忆事件引用匹配（"刚才那个"）、查询文本中出现的关键词与购物车内商品的语义匹配。最后兜底：购物车唯一商品或最新推荐的首个商品。多 SKU 商品——比如同一个防晒有 30ml 和 50ml 两种规格——加购时必须选规格。ActionExecutor 检测到多 SKU会拒绝加购并触发规格选择器 SSE 事件，前端弹出选择 UI。这保证用户不会不小心买了不想买的规格。批量操作也支持——"把这两个都加入购物车""删除购物车里的所有防晒"——系统识别"都""所有""全部"等批量信号，一次执行多个操作。

---
  7. 流式输出 → 20+ SSE 事件类型 + 推荐流式协议

  设计哲学： SSE 事件类型不是越多越好——每种事件对应一种前端 UI
  状态变更。事件设计的原则是"后端告诉前端发生了什么，前端决定怎么展示"。

  面试回答：流式输出我用 SSE 协议，设计了 20 多种事件类型。分成四类：进度类（告诉用户系统在干什么）、内容类（推荐文案逐 token 或逐section 展示）、数据类（商品卡片、购物车快照、规格选择器）、控制类（页面导航指令、流结束信号）。最值得讲的是推荐流式协议。LLM 可能会一次推荐 3-5 个商品，如果等全部生成完再展示，用户会等很久。我设计了一个 SECTION标记协议——LLM 输出中插入 [[SECTION:1]]...[[END_SECTION]] 标记——后端流式发出，前端增量解析。即使 token边界刚好切在标记中间，解析器也能正确恢复。前端打字机效果根据状态动态调整步长和延迟——已完成段落快速回放（6-8 字符/步），流式段落慢速跟随（2-6字符/步），去重检测防止重复展示。进度事件独立于 LLM 生成——每 700ms交错发送进度更新（"正在理解你的需求→正在筛选商品→正在生成推荐"），用户不会面对一个空白页面干等。

---
  8. 对话流控制 → 17 种流程 + 优先级链

  设计哲学： Agent 的对话不是"意图→回复"的一对一映射，而是要在 17 种可能的流程中选一个，同时支持中途切换。

  面试回答：Agent 收到一条消息后，不只是判断意图然后生成回复。我设计了一个对话流决策层——DialogueFlowController——在意图识别之后、生成回复之前，决定"这一轮对话应该走哪条流程"。17 种流程——问候、推荐、筛选、细化、澄清、对比、商品问答、场景捆绑、购物车操作、结账、偏好更新、无结果、闲聊、越界、无效、详情、结账引导。

决策逻辑是一个优先级链：先判断是否无效或越界 → 是否有购物车操作和结账信号 → 是否在更新偏好 → 是否为闲聊 →是否在对比或看详情 → 是否需要场景捆绑 → 是否需要澄清 → 是否有排除条件 → 是否为筛选或细化 → 默认走推荐。

话题切换是这里面最复杂的。用户可能在推荐中说"等一下，购物车里有什么？"——系统需要判断这是话题切换还是延续。我通过_should_lock_current_topic() 和 _message_suggests_topic_switch()两个函数来判断，前者检测延续信号（"有便宜一点的吗"），后者检测跨类目信号（"看看数码产品"）。



---
  10. 多模态 → 图片搜索管线

  设计哲学： 用户上传一张图片说"我想找类似风格的"，这不是纯 CV 任务——需要 VLM 理解 + 文本检索融合。

  面试回答：图片搜索我做了端到端管线。用户上传图片 → VisionAnalyzer 调 Doubao VLM 分析视觉属性（颜色、风格、品类）→VisualQueryBuilder 把视觉属性融合到文本查询中 → VisualProductMatcher 做图片到商品的匹配。匹配分三策略：fixture匹配（商品图直接对比）、别名匹配（视觉描述中的品类名映射到商品类别）、特征相似度（颜色/风格向量匹配）。如果 VLM不可用，降级到关键词匹配（confidence 约 0.48），虽然弱但不阻断流程。这个模块的当前限制是 Doubao 视觉模型的能力有限——复杂场景的理解不如 GPT-4V——但我设计的管线是模型无关的，换 VLM只需要替换 VisionAnalyzer 的实现。

## 一、项目介绍题

### Q1: 请简单介绍你的项目

> 我构建了一个 RAG 多轮电商导购 AI Agent 系统。用户可以用自然语言描述需求（如"帮我推荐适合混油皮的清爽防晒，预算 300 以内"），系统理解意图后从真实商品库检索、打分、排序，通过 LLM 生成有理由的推荐，并通过 SSE 流式返回给 Android 客户端。系统还支持多轮对话、个性化记忆、自然语言购物车操作、图片搜索和结账引导。

### Q2: 这个项目解决的核心问题是什么？

1. **搜索效率**：用户不需要自己从大量商品中筛选，Agent 理解复杂需求并直接给出推荐
2. **推荐可信度**：基于真实商品库 + 事实边界隔离 + 输出校验，防止 LLM 编造
3. **个性化**：记住用户偏好，千人千面的导购体验
4. **转化闭环**：推荐→比较→加购→结账，一站式完成

### Q3. 这个项目遇到了什么困难？

我做了什么，核心思路是，你为什么这么做，还考虑过什么方案，为什么没选。

这个项目中最大的困难，是如何让系统在多轮对话中持续理解用户不断变化的需求，同时保证后续业务操作的准确性。

电商导购通常不是一轮对话就能完成。例如用户一开始只说“推荐一款防晒”，需求比较模糊，系统还需要通过追问逐步补充肤质、预算、使用场景和肤感偏好。在这个过程中，用户的意图也可能随时切换，比如上一轮还在推荐商品，下一轮就说“把第一个加入购物车”，之后又问“之前推荐的第三款是什么”。这要求系统既能继承有效约束，又能识别流程切换，还要准确回溯历史商品。

如果只依赖大模型和原始对话上下文，会存在两个问题：一是模型可能混淆新旧需求，例如切换商品类目后仍然继承之前的条件；二是购物车、结算和商品指代都属于确定性业务操作，仅靠大模型推断难以保证操作对象和执行结果准确。

为了解决这个问题，我们设计了三层状态与记忆机制。第一层是对话状态，记录当前流程、商品类目、预算、正向条件和排除条件，负责判断哪些需求应该继承、合并或在话题切换时清空。第二层是事件记忆，记录每次推荐、详情查看和购物车操作的结果，并维护“第一款”“刚才那个”等表达到具体 SKU 的映射，用于跨轮指代消解和历史回溯。第三层是用户画像，维护用户长期的品牌、风格和表达偏好，用于个性化推荐排序和回复生成。

同时，我们明确划分了大模型和确定性代码的任务边界。大模型主要负责复杂意图理解、约束抽取和推荐理由生成；状态机和规则负责最终流程路由，购物车增删、商品比较和结算等操作则由确定性代码执行。也就是说，大模型负责理解“用户想做什么”，代码负责保证“业务动作准确执行”。

最终形成了“状态机控制流程、三层记忆维护上下文、大模型增强理解、代码保证确定性、用户画像支持个性化”的整体方案。

### Q4. 意图识别怎么做的

第一层：严格模板 _parse_strict_template

只处理非常简单、风险较低的句式，例如：
推荐一款跑鞋
想要一个背包
选择一款防晒
预算500元
一旦包含以下复杂信息，就不会走本地模板：
否定：“不要、排除、拒绝”
上下文：“刚才、之前、这款”
购物车：“加购、删除、结算”
比较：“哪个、哪款、对比”
多动作：“然后、同时、顺便”
场景组合：“一套、清单、方案”
这样设计的目的，是避免简单正则错误处理复杂语义。

第二层：豆包 _parse_with_llm
只要没有命中严格模板，就调用：
self.llm_client.resolve_user_intent(...)
发送给豆包的上下文比较完整，包括：
当前用户消息。
系统支持的全部意图。
商品库实际存在的大类和子类。
当前对话类目和约束。
最近推荐的商品。
当前购物车商品。
一系列意图判断规则。
豆包返回结构化 JSON 后，再由：
_parsed_query_from_llm_payload()
进行二次校验和修正。
这一步不是完全相信大模型，而是使用本地规则纠正它，例如：
豆包把单个“背包”误判为场景搭配，会被改回推荐。
豆包把普通追问误判为比较，但用户没有真实比较词，会被改回推荐或追选。
豆包返回不存在的商品类目时，会根据商品库进行归一化。
本地重新提取价格、品牌和否定条件，补充豆包漏掉的字段。
结合上一轮状态判断是否继承上下文。

第三层：规则降级 _parse_legacy_rule
当豆包不可用或返回无效结果时，模块会降级到：
关键词规则识别意图。
text2vec 小模型修正意图。
规则提取价格、类目、品牌和属性。
根据对话状态锁定当前主题。
构造简单的 IntentPlan。

因此系统即使没有大模型，也不会直接崩溃。

### Q6: 混合检索的 7 维权重是如何设计的？

把自然语言转化成结构化条件，例如价格约束、品牌约束、正向需求、反向需求。这个是用来硬约束过滤的
然后检索的时候首先采用查询增强检索，对用户原始句子进行同义词扩展，比如用户说不想用太黏腻的，会进一步扩展成补水保湿推荐。
在商品这一侧，聚合每个商品的信息成一个文档，具体包括商品名称、品牌、价格、亮点、用户评论、官方回复等。这里没有对文档进行切块，因为我最终要检索的对象就是一个“商品”，商品文档通常也比较短，所以就把一个商品当成了一个检索单位。
第一阶段：硬过滤。从类目、价格、品牌、负向约束先排除掉首先不合要求的商品。
第二阶段：多维评分：
关键词匹配分（标点符号、空格切割、按照长度截断、取词频前20的词，最终得分是商品文档中出现的关键词数量除以查询中的关键词总数量）
轻量语义分（字符级二元组，计算两个，一个是Jaccard相似度，交集/并集，一个是Containment覆盖率，交集/查询长度，因为商品文档比较长，取并集的时候会使得相似度偏低，所以两个一起用，两个相似度是集合平均，要求两个指标都不能太低sqrt(J * C)）
BGE和text2vec语义分, BGE适合信息检索，它的训练目标和使用方式重视Query-Document的相关性排序，text2vec比较适合比较中文句子语义相似度，补充BGE对中文口语、短句和同义表达的识别能力。

结构化约束分（正向约束出现在商品文档里的数目/正向约束数）
商品增强字段分（为商品增加了一些贴近用户口语和使用场景的标签，比如“走路不累的鞋”，如果用户问题命中了这些字段，就给商品额外加分）
用户偏好分（根据用户过去积累的长期偏好，如偏好品牌、偏好风格、排除风格，对检索到的商品做一些轻微加分或减分）
价格适配分（若用户给出预算，偏向于预算的 75%）
reranker精排分（bge-reranker，把查询和商品文档联合输入模型，输出相关性分数）

- **有 Reranker 时**：keyword 0.18, semantic 0.24, constraint 0.22, enhancement 0.08, price_fit 0.10, preference 0.08, reranker 0.10
- **无 Reranker 时**：keyword 0.24, semantic 0.28, constraint 0.22, enhancement 0.12, price_fit 0.10, preference 0.04

### Q7: Agent 的状态管理是怎么做的？

状态管理分为三层。第一层是对话状态，追踪当前处于哪种对话流程、聚焦哪个商品类目、累积了哪些筛选条件——价格区间、正向特征、排除条件、品牌黑白名单。这些条件同话题下逐轮合并，切换类目时清空。购物车、最近消息等会话级状态不受话题切换影响。

第二层是结构化事件记忆，记录推荐、详情、比较和购物车操作等业务动作真正执行成功后的结果。推荐事件会保存 rank 到 SKU 的映射，使用户后续可以通过自然语言直接定位具体商品。详情事件维护当前焦点商品，使“这个”“它”优先指向刚查看过详情的 SKU；购物车事件通过 active_cart_sku_id 绑定“刚才加购的”等表达。详情、比较和购物车事件还可以通过 source_event_id 关联回来源推荐事件，用于指代消解和行为溯源。

第三层是跨会话的长期用户记忆，内部包含原始历史和用户画像两个部分。原始历史由 UserHistoryStore 持久化保存每一轮的用户输入、系统回复、推荐结果和完整 SessionState 快照，服务重启后可以据此恢复会话状态。用户画像又包括三类信息：第一类是 semantic_memory 计数器，每轮结束后从 ParsedQuery 和业务结果中提取类目、特征、品牌、价格、推荐、加购等结构化信号进行累计；第二类是 structured_profile，在会话结束或满足刷新条件时，根据历史生成说话风格、价格偏好、品牌倾向和决策习惯等更高层画像；第三类是用户明确声明的长期偏好，例如“以后不要推荐耐克”或“我通常喜欢宽松款”，这类信息通过独立的偏好更新路径保存。

在使用优先级上，本轮用户明确提出的需求最高，会话状态只补充本轮没有说明的信息，事件记忆负责定位具体商品，长期画像主要用于推荐重排序和回复个性化。长期偏好通常作为软排序信号，不会覆盖本轮的价格上限、排除品牌和否定条件等硬约束。

### Q8: 如何处理多轮对话中的上下文继承？

1. **话题锁定**：`_should_lock_current_topic()` 检测是否延续上一轮话题
2. **约束合并**：`context_merge` 将当前轮次的约束与历史约束合并
3. **指代消解**：8 个别名/排名 + 代词绑定 + 事件链追踪
4. **意图继承**：REFINE/FILTER 意图自动继承上一轮类别

**代码证据**：`shopping_agent.py` — `_stream_chat_core()` 阶段 3

关于上下文继承，我们主要通过“上下文信号识别、话题判断、约束更新和指代消解”四个环节协作完成。

首先，在查询理解阶段，系统会识别本轮是否存在上下文继承信号。信号主要有三类：一是 ParsedQuery 直接标记了 inherit_context；二是本轮意图属于 REFINE（便宜点，贵了，换一个），说明用户想在上一轮结果上继续调整；三是用户表达中出现“再、换、更、继续、刚才、前面”等延续词。

第二步是判断本轮属于话题延续还是话题切换。系统会结合本轮是否明确提出了新类目、当前类目是否与上一轮一致，以及是否存在继承信号进行判断。例如用户先说“推荐一款防晒”，SessionState 会记录当前主题为“美妆护肤/防晒”；下一轮只说“再便宜一点”，虽然没有重复商品类目，但因为意图是 REFINE，同时存在“再”这个延续信号，系统会判断仍然处在防晒主题下。如果用户明确改说“推荐一款手机”，则会识别为新的商品范围，不再继承原来的防晒主题。

第三步是约束合并或重置。如果属于同一话题并且需要继承，系统会将上一轮 active_constraints 与本轮新条件合并。价格上下限这类标量字段采用“本轮优先”：本轮有明确值就覆盖，没有值才继承；特征、品牌包含和品牌排除等列表字段则去重合并。相反，如果检测到明确的新类目，上一轮的价格、品牌、正向特征、否定条件和场景信息都不会带入新话题。

第四步是通过事件记忆完成商品指代消解。推荐动作成功后，系统会记录 RecommendationEvent，并预生成 rank 到 SKU 的别名映射。例如 rank 为1的商品会对应“第一个”“第一款”“第1个”“一号”等表达，用户说“第一个太贵了”时，可以从最近一次推荐事件中直接定位到具体 SKU。“这个”或“它”优先指向刚查看详情的商品，否则指向最近推荐的第一款；“刚才加购的”则通过购物车事件中的 active_cart_sku_id 独立解析。加购本身不会改变推荐 rank 映射，但如果后续产生了新的推荐事件，序号引用会以最新推荐结果为准。

因此，这套机制实际上同时解决了两个问题：SessionState 负责判断“用户是否仍在讨论上一轮商品，以及应继承哪些条件”，EventMemory 负责判断“用户提到的某个序号或代词到底对应哪个 SKU”。

### Q9: 系统的容错和降级策略是什么？

按照故障来源，我将异常分为两类：外部依赖不可用和内部业务管线失败。

第一类是外部依赖不可用，主要是豆包大模型接口出现网络异常、调用超时或返回格式不符合预期。由于大模型参与了意图理解、自然语言生成和用户画像更新，所以我没有设计一个统一的简单兜底，而是针对每个环节分别建立独立的降级路径，尽量把故障限制在当前环节内。

在意图理解环节，系统采用分层识别机制。大模型识别失败后，会自动回退到本地规则和轻量语义匹配，通过类别别名、关键词和 text2vec 相似度继续判断用户意图，保证后续路由不中断。

在回复生成环节，如果真实大模型不可用，系统会切换到本地 MockLLMClient。它基于规则和场景模板生成结构完整的回复。降级后的语言表达可能没有大模型自然，但商品、价格和操作结果都来自系统中的确定性数据，因此不会因为模型不可用而编造业务事实。

在用户画像更新环节，系统采用“LLM摘要、语义统计、关键词规则”的梯次降级方式。即使大模型无法生成画像摘要，也可以根据用户历史行为和关键词统计，维护一个最低可用的偏好画像。

第二类是内部管线失败，最典型的是商品检索结果为空。例如用户要求“100元以内的SK-II”，品牌和价格条件之间可能无法同时满足，经过硬过滤后候选集就会变成空集。

对于这种情况，系统不会立即结束推荐，而是采用渐进式检索松弛机制。首先按照完整约束检索；如果没有结果，再逐步放宽非安全性条件，例如放宽价格区间、扩大类目范围，或者调整一般性的品牌和负向偏好约束。每一级只放松一个维度，而不是一次性清除全部条件，避免推荐结果与用户需求突然发生较大偏离。

需要特别说明的是，安全性约束不会被放宽。例如儿童安全、过敏原和明确风险条件，即使没有候选商品，也不会为了返回结果而强行推荐。

每次约束松弛都会被结构化记录，并转换为用户可以理解的说明。例如系统会告诉用户：“暂时没有找到完全满足预算的商品，因此适当放宽了价格范围，并优先推荐价格最接近的同类商品。”这样用户不仅能看到结果，也能理解系统为什么推荐这些商品。

如果经过合理放宽后仍然没有符合要求的商品，系统会返回澄清问题或明确的无结果提示，而不是给出与用户需求完全无关的商品。

除了针对具体环节的降级之外，系统还有一层全局异常保护。整个对话流由统一的异常处理机制包裹。即使前面的意图识别、检索、生成和降级链路都出现了未预期异常，后端仍然会输出结构完整的 error 事件和 done 结束事件。前端可以据此结束加载状态，并向用户显示“系统暂时遇到问题，请重试”，避免出现一直加载、白屏或者会话无响应。

### Q10: 如何防止 LLM 幻觉？

关于如何减少大模型幻觉，我通常会先从业界常见的方法讲起。

主流方法大致可以分为五类。

第一类是 Prompt 约束。通过系统提示词明确模型的角色、允许使用的信息范围和禁止行为，例如要求模型只能依据给定资料回答，资料中没有的信息要明确说明无法确认。同时可以使用 JSON Schema、Function Calling 等结构化输出方式，减少模型自由发挥的空间。

第二类是 RAG，也就是检索增强生成。系统先从知识库、数据库或业务系统中检索相关事实，再把检索结果提供给模型生成回答。相比让模型完全依赖参数记忆，RAG能够把回答建立在当前、可验证的外部数据上。为了提高召回质量，还可以采用关键词检索、语义检索、重排序以及引用溯源等方式。

第三类是输出校验。模型生成结果后，再通过规则、知识库比对、NLI模型或独立模型审核其中的商品名称、价格、数字和事实是否与参考信息一致。如果校验失败，可以修复、重新生成，或者降级为安全模板。

第四类是系统架构约束。对于库存查询、购物车操作、支付和订单修改等确定性任务，不应该让大模型直接决定，而应该由程序、数据库和工具完成。大模型主要负责意图理解和自然语言生成。高风险场景还可以增加人工审核、多模型交叉验证以及低置信度降级机制。

第五类是模型训练和对齐，例如使用领域指令微调、RLHF或DPO，让模型更好地学习领域边界，并学会在证据不足时承认无法回答。不过这一类成本较高，通常更适合有自有模型训练能力的团队。

在我们的电商导购项目中，主要采用了“检索接地、Prompt约束、结果校验和确定性代码执行”四层机制。

首先，在数据来源上，我们不会让模型凭空生成商品。系统会先根据用户需求进行类别和价格等硬过滤，再结合关键词、语义相似度、用户偏好、标签和价格适配度等因素进行排序。最终只把检索到的候选商品交给大模型。

其次，我们会把候选商品的名称、品牌、价格、标签、适用场景、评价和风险信息整理成 Verified Product Facts，注入系统提示词。提示词明确规定，模型只能基于这些事实生成内容，不允许编造商品、价格、库存、优惠、功效或者商品库中不存在的参数。对于缺失信息，也要求模型明确说明商品库暂未提供，而不是自行补全。

第三，在生成结果之后，我们还设置了 ResponseValidator。它会检查回答中出现的商品名称是否属于当前候选集，并通过正则提取价格，与商品库中的真实价格进行比对。如果出现不存在的商品名或错误价格，就不会直接把结果返回给用户，而是触发安全降级或使用经过验证的候选商品重新组织回答。

第四，也是我们认为最重要的一点，是明确划分大模型和确定性代码的职责边界。像购物车增删改查、商品ID解析、价格过滤、规格选择和状态写入等操作，都由代码和工具完成，大模型不能直接修改业务状态。大模型主要负责复杂意图识别、需求总结、商品比较以及推荐理由的自然语言生成。

例如，当用户说“把刚才第二款加入购物车”时，大模型可以帮助判断这是一个加购意图，但“第二款”具体对应哪个SKU，会通过之前推荐事件中保存的 rank-to-SKU 映射确定，真正的加购操作也由确定性代码执行，而不是让模型猜测商品。

如果用户条件不完整、检索结果不足或者生成结果未通过校验，系统不会强行给出一个商品，而是进入澄清、降级或安全回复流程。

因此，我们项目的核心思路可以总结为：能由数据库、规则和代码确定的内容，就不交给大模型；必须使用大模型时，先提供经过检索验证的事实，再限制生成范围，最后对结果进行校验。这样并不能从理论上完全消除幻觉，但能够显著降低商品、价格和业务操作方面的事实性错误。

### Q12: 用户记忆如何跨会话持久化？

在跨会话记忆的保存和管理上，我们将记忆分为会话级状态和用户级长期画像，两者的保存时机和作用不同。

首先，会话中的对话状态和事件记忆会在一轮请求的处理过程中实时更新。

例如，意图识别完成后会更新当前对话流程；识别到价格、品牌和功能要求后，会更新结构化约束；完成商品推荐后，会记录推荐事件以及排名到 SKU 的映射；发生加购操作后，会更新购物车状态和购物车事件。

这些运行时状态首先保存在内存中的 SessionMemory 中，便于当前会话快速访问。每轮对话结束后，系统会调用保存逻辑，将本轮对话记录和完整的 SessionState 快照同步写入本地 session 文件。

因此，即使服务重启导致内存状态丢失，只要用户继续原来的 session，系统就可以从本地读取 state_snapshot，反序列化后重新注入 SessionMemory，恢复之前的类目、筛选条件、推荐记录、事件记忆和购物车状态。

对于真正跨不同 session 使用的信息，系统会进一步更新用户级长期画像。

长期画像主要分为两部分。第一部分是规则型画像，例如用户对不同类目、品牌和商品特征的提及、偏好和排斥，以及加购等行为统计。这部分在每轮对话结束后通过规则增量更新，并同步写入用户的 profile 文件。

第二部分是自然语言画像摘要和更高层的结构化画像，例如用户的价格敏感程度、决策习惯和表达风格。这部分不需要每轮都调用大模型，而是累计一定轮次，例如每三轮，通过后台任务异步更新，从而降低当前请求的延迟和模型调用成本。

因此，同一个 session 恢复时会加载完整会话状态；用户创建新 session 时，不会直接继承上一次正在比较的商品等临时状态，但会加载长期用户画像，用于新的检索、排序和回复生成。

在多轮对话的上下文管理上，我们也不会把全部历史对话原文都放入 Prompt，而是采用结构化状态和有界上下文构建。

每轮进入 Prompt 的内容主要包括五部分：

第一部分是固定的系统提示词，包括模型角色、事实边界和输出要求。

第二部分是用户本轮输入。

第三部分是当前会话的结构化状态，例如当前类目，以及已经确认的价格、品牌、功能和排除条件。

第四部分是经过筛选的个性化信息，包括用户画像摘要、显式偏好、当前购物车摘要，以及与本轮需求最相关的少量历史证据。

第五部分是经过检索、过滤和重排序后的候选商品事实，供模型生成有依据的推荐理由、商品比较或问答回复。

对于可能不断增长的历史信息，我们设置了明确的数量和长度上限。历史记录不会全部进入 Prompt，而是根据当前类目、子类目、关键词重合度和购物车行为等因素进行相关性打分，只选择得分最高的少量记录，例如 Top 5，并对每条记录进行长度截断。

最近消息、完整事件记忆和全部历史会话仍然会保存在系统中，但主要由后端代码用于状态跟踪、指代消解和业务操作，不会原样交给大模型。

例如用户说“把刚才第二款加入购物车”时，系统会通过推荐事件中的 rank-to-SKU 映射确定具体商品，而不是依赖大模型重新阅读完整聊天记录并猜测“第二款”指什么。

所以，我们的设计可以概括为：请求处理中实时更新会话状态，每轮结束后持久化会话快照和长期画像；下一轮再通过结构化状态、事件记忆和相关历史筛选，共同构建完成当前任务所需的最小充分上下文。

### Q13: 个性化怎么实现的？

我们项目的个性化不是让大模型直接根据聊天记录猜测用户喜好，而是先由规则、统计和画像服务提取个性化信号，再将这些信号用于商品重排和回复生成。

整体上，个性化信息主要来自四个方面：长期用户画像、语义记忆、购物车感知和相似用户参考。此外，系统还会根据商品领域设置不同的导购表达风格。

第一部分是长期用户画像。

系统会将用户的历史偏好持久化到 profile.json 中，包括自然语言画像摘要和结构化画像。结构化画像主要描述用户的价格偏好、品牌偏好、商品类别偏好、信息关注点、表达风格和决策风格。

例如，系统可能总结出用户偏好运动装备，通常关注500元以内的商品，更在意轻量、透气和性价比，并且习惯先看结论，再看具体理由。

这部分画像不需要每轮都调用大模型，而是累计一定交互轮次后，例如每三轮，在后台异步刷新，从而降低当前请求的延迟和模型调用成本。

第二部分是语义记忆。

与大模型画像不同，语义记忆完全通过规则进行增量统计，每轮都会更新，不依赖大模型。

系统会统计用户经常关注的商品类目、功能特征和品牌，记录用户表达过的价格范围、负面约束以及购物车中的商品。例如：

- 用户多次查询运动类商品；
- 多次提到轻量、透气；
- 经常关注Nike；
- 多次提出预算不超过500元；
- 明确排斥太重或太甜的商品。

这类信息以计数、价格信号和记忆卡片等结构化形式保存。它的优点是稳定、可解释，即使大模型画像更新失败，也能提供最低可用的个性化能力。

第三部分是购物车感知个性化。

系统会根据当前购物车中的商品反向推断用户当前的消费场景和搭配需求。

一方面，系统会根据购物车商品的品牌、类目、价格带和功能标签，推导出诸如“价格敏感”“Apple生态”“高端护肤”“运动训练”“户外装备”等场景标签。

我们设计了一套本地搭配规则。例如：

- 购物车中有MacBook时，提高苹果耳机、平板和办公配件的优先级；
- 有iPhone时，优先考虑同生态的耳机、手表或充电设备；
- 有精华时，可以补充面霜、眼霜等护肤步骤；
- 有跑鞋时，可以推荐运动袜、速干上衣或运动短裤。

购物车个性化主要通过软加分影响候选商品排序，例如品牌生态匹配、搭配子类命中和价格带接近都会获得一定加分，但不会直接删除其他商品。

因此，它不是传统意义上的“买过什么就继续推荐什么”，而是基于商品之间的品类生态和互补关系进行场景化推荐。

第四部分是相似用户参考，也就是项目中的轻量级协同机制。

系统会将当前用户的画像摘要、结构化偏好、近期相关历史和当前需求组合成一份风格文档，再与参考用户池中的用户画像进行比较。

相似度主要由三部分组成：

- BGE和text2vec计算的语义相似度；
- Jaccard词汇重合度；
- 当前类目和子类目的匹配度。

系统会选择达到阈值的Top-K相似用户，通常最多选择3个，再提取他们的表达风格和少量Few-shot示例。

需要强调的是，这部分相似用户信息只用于调整回复节奏、解释重点和信息粒度，不直接决定推荐什么商品。例如，相似用户都习惯先看结论，系统就可以先给出推荐结果，再补充轻量、透气和价格方面的理由，但不能把其他用户购买过的商品直接推荐给当前用户。

除了这四类信息来源，系统还会根据当前商品领域设置不同的导购风格。例如美妆场景更关注肤质、成分和使用感，数码场景更关注参数、性能和生态兼容性，运动场景更强调使用场景、舒适性和功能搭配。

这些个性化信号最终会在两个位置发挥作用。

第一是在检索和排序阶段。

用户当前明确提出的价格、品牌、功能和排除条件会作为硬约束参与过滤；长期偏好、语义统计和购物车标签则作为软信号，对候选商品进行加权重排。

第二是在回复生成阶段。

PersonalizationService会根据当前请求构建个性化上下文，PromptBuilder再将用户画像摘要、结构化偏好、相关历史证据、Few-shot示例、相似用户风格以及购物车摘要注入Prompt，引导大模型采用更符合用户习惯的表达方式。

不过，个性化并不是无条件启用的，我们还设置了三层控制机制。

第一层是当前需求优先。

用户本轮明确表达的需求始终是硬约束，历史偏好和购物车推断只作为软参考。当两者发生冲突时，必须服从用户当前需求。

例如用户长期偏好Nike，但本轮明确说“不要Nike”，系统必须排除Nike，而不能因为历史画像继续推荐。

第二层是隐私模式控制。

系统提供full、semantic和off三种个性化模式：

- full模式可以使用用户画像、经过筛选的历史证据、Few-shot和相似用户参考；
- semantic模式只使用类目、品牌、特征等结构化统计，不把历史对话原文放入Prompt；
- off模式关闭用户历史个性化，只保留当前请求所需的基础领域风格和必要的购物车信息。

第三层是冷启动保护。

当用户交互轮次较少、还没有形成稳定画像时，系统不会过早启用完整个性化，而是先根据本轮明确需求完成推荐，同时逐步积累行为数据。达到一定轮次或画像稳定后，再启用历史证据和相似用户参考，避免因为少量行为对用户产生错误判断。

例如用户输入“推荐一双500元以内的轻量跑鞋”时，系统首先将跑鞋、500元以内和轻量作为当前硬约束；然后读取长期画像中的运动偏好和性价比关注点，结合语义记忆中的轻量、透气等高频特征，再根据购物车中已有的跑鞋或运动袜推断运动训练场景。

如果用户画像已经稳定，系统还会筛选与本轮最相关的历史记录，并找到表达风格相近的参考用户。最终，商品排序会适当偏向符合运动场景、价格带和搭配关系的商品，回复则采用用户习惯的“先给结论、再说明轻量、透气和性价比”的方式。

所以，我们项目中的个性化可以概括为：规则负责硬约束和购物车搭配，统计负责长期偏好积累，大模型负责画像总结和自然语言表达，相似用户机制负责补充回复风格。所有历史个性化信息都是软参考，用户本轮明确需求始终拥有最高优先级。



协同过滤：

我们项目中实现了一种轻量级的相似用户协同机制，但它和传统推荐系统中的协同过滤有所不同。

传统协同过滤通常基于用户—商品交互矩阵，例如点击、评分或购买记录，通过 UserCF、ItemCF、SVD 或 ALS 等算法预测用户可能喜欢的商品。

而我们的项目目前缺少大规模真实用户—商品行为数据，因此没有直接构建评分矩阵，也没有让协同过滤参与商品召回和排序。我们采用的是一种面向对话个性化的相似用户检索机制，主要作用是调整大模型的回复风格、解释重点和信息粒度。

整个流程可以分为五步。

第一步是构建当前用户的风格文档。

系统会把当前用户的画像摘要、历史摘要、结构化画像、经常关注的类目和商品特征、表达风格，以及本轮的类目和筛选条件拼接成一份文本表示。

如果用户已经积累了足够的历史数据，还可以加入少量近期对话，帮助描述用户习惯的表达方式和决策偏好。

这份风格文档不是商品推荐查询，而是对当前用户的偏好和沟通方式进行文本化表示。

第二步是构建参考用户池。

项目中预设了一批覆盖美妆、数码、服饰、运动和食品等领域的种子用户，每个参考用户都有预先构建的历史对话和用户画像。同时，系统也会把本地已经积累了有效历史数据的其他用户加入候选池。

使用种子用户的主要原因是解决冷启动问题。在缺少大规模真实用户数据的情况下，新用户也能找到具有一定相似度的参考对象。

第三步是计算用户之间的相似度。

系统会从三个维度比较当前用户和参考用户。

第一是语义相似度。分别使用 BGE 和 text2vec 对两份风格文档进行向量编码，再计算余弦相似度。

第二是词汇相似度，通过 Jaccard 系数计算当前用户和参考用户在类目、特征和风格词上的重合程度。

第三是业务类目匹配度，例如两名用户当前关注的主类目、子类目是否一致，参考用户的历史中是否出现过相同领域。

最终以语义相似度为主、类目匹配为辅进行加权融合。如果本地语义模型不可用，系统还可以回退到基于关键词重合度的轻量计算，保证该功能不会阻塞主流程。

第四步是通过阈值和 Top-K 选择参考用户。

系统会对候选用户按综合得分排序，通常最多选择三个相似用户，并设置最低相似度阈值，防止把明显不相关的用户强行作为参考。

只有当当前用户积累了一定的有效对话轮次，或者已经形成相对稳定的画像时，才会启用这部分个性化逻辑。这样可以避免在用户信息非常少时，过早形成错误判断。

第五步是提取参考信息并注入 Prompt。

系统主要从相似用户中提取两类内容。

第一类是画像风格，例如这个用户偏好简洁直接的表达、习惯先看结论，或者更关注性价比和功能细节。

第二类是少量相关的历史问答示例，用作 Few-shot，帮助模型学习类似用户更容易接受的回复节奏和解释方式。

这里有一个非常重要的约束：相似用户的信息只影响回复的表达方式，不能影响当前用户的商品事实和业务决策。

系统会明确告诉模型，只学习参考用户的语气、结构和解释重点，不能复制原句，也不能把参考用户曾经购买或推荐过的商品带入当前回答。

当前用户最终看到哪些商品，仍然由当前需求、商品库、硬约束过滤、检索和排序结果决定。

例如，两名用户都关注轻量运动装备，并且都偏好简洁直接的回答，系统可能参考相似用户的表达方式，先给出推荐结论，再简要解释重量、透气性和价格。但不会因为参考用户购买过某双鞋，就直接把这双鞋推荐给当前用户。

因此，这个机制本质上不是传统的商品协同过滤，而是“基于用户画像和对话历史的相似用户检索”。它通过寻找表达习惯和关注重点相似的用户，为大模型提供风格层面的 Few-shot 参考。

它的优势是在缺少大规模用户—商品矩阵时，也能实现一定程度的跨用户个性化；局限是目前参考用户池规模较小，更多属于工程上的轻量实现。未来如果积累了足够的真实点击、收藏、加购和购买数据，可以进一步增加传统 UserCF、ItemCF 或矩阵分解，让协同信息真正参与商品召回和排序。

## 十一、八股

### Q1. RAG是什么？

定义->流程->价值->局限->项目结合

RAG是检索增强生成。它的核心思想是让大模型在生成答案之前，先从外部知识库检索与用户问题相关的内容，再把检索结果和用户问题一起交给大模型生成答案。

典型流程包括文档切分->embedding向量化->向量库存储->相似度检索->reranker重排序。

它主要解决大模型只是过时，不了解私有数据和容易产生幻觉的问题。相比微调，RAG更适合频繁更新的知识，但它的最终结果会受到切块、检索召回率和上下文质量的影响。

在我们的项目中，用户提出需求后，系统会先从真实商品库中进行硬过滤和多维排序，再把候选商品属性交给大模型生成推荐理由，从而避免大模型凭空编造商品和参数。

### Q2.你知道哪些Agent范式

我了解的Agent范式主要有ReAct，Plan-and-Execute，Reflection，Router，多Agent协作。

ReAct是“推理->行动->观察”循环，适合需要动态调用工具的任务，可以根据工具调用的结果调整后续步骤，问题在于容易陷入重复调用或无限循环。

Plan-and-Excute是先规划后执行，适合长任务，多步骤任务。

Reflection是让Agent对自己的结果进行检查，将失败原因、评价结果写入长期记忆，并用于后续任务，适合代码生成、数学推理、文档审核等任务。

Router路由范式负责识别任务类型，再把任务交给合适的模块或Agent，适合业务边界明确，不同任务处理逻辑差异较大的系统。

在多Agent系统中，Supervisor是常见的管理者模式，Supervisor负责拆解任务，分配子任务，判断下一步调用哪个子Agent，检查任务是否完成，汇总最终结果。

我们项目采用的是状态机驱动、规则优先、LLM增强的Agent架构，系统先通过状态机把用户请求路由到推荐、购物车、比较、商品问答或澄清等流程，再由 Task Planner 为每种流程生成固定的任务序列。整体上是规则优先、LLM 增强：规则和代码负责价格过滤、商品检索、购物车操作等确定性业务，大模型主要负责复杂意图理解和自然语言生成。

### Q3.项目有用什么Agent框架吗

我们项目没有直接使用 LangGraph、LangChain Agent 或 AutoGen 这类通用 Agent 框架，而是基于 FastAPI 自研了一套面向电商导购场景的 Agent 编排框架。

整体采用状态机加 Pipeline 的架构。ShoppingAgent 作为统一编排入口，内部包含输入预处理、需求理解、对话流程控制、任务规划、商品检索与排序、回答生成、结果校验以及前端事件生成等模块。系统先由 DialogueFlowController 根据用户意图和对话状态，将请求路由到商品推荐、购物车、商品比较、商品问答或澄清等流程，再由 Task Planner 将不同流程映射为预定义的任务序列。

当时没有直接使用 LangGraph，主要有三个原因。

第一，项目的核心业务路径比较明确。推荐、比较、加购等流程大多可以提前定义，不需要大模型在执行过程中不断进行自主规划和循环决策。

第二，电商业务对确定性要求比较高。价格过滤、商品真实性、购物车修改和前端操作都不能完全交给大模型，因此我们更倾向于通过代码、规则和状态机精确控制每一步。

第三，项目当时更关注快速落地和业务定制。自研编排可以直接适配商品检索、事件记忆、前端 SSE 事件以及结果校验逻辑，减少引入通用框架后的适配成本。

如果使用 LangGraph 进行重构，我会把当前架构映射为一个有状态图。将用户输入、对话状态、用户偏好、当前流程、候选商品和校验结果定义为统一的 State；把需求理解、流程路由、商品检索、过滤重排、回答生成、结果校验和前端事件生成分别定义为 Node；再通过 Conditional Edge，根据意图将请求分发到推荐、购物车、比较、商品问答或澄清等分支。

对于校验不通过、检索结果不足或者用户条件不完整的情况，还可以通过条件边回到重新检索或澄清节点。后续如果需要增加断点恢复、人工审核、动态重规划或者更复杂的多分支流程，LangGraph 会比当前的自研状态机更有优势。

### Q4. deepseek架构有了解过吗？

我对 DeepSeek 的模型架构有一定了解。以 DeepSeek-V3 为例，它整体仍然是 Decoder-only Transformer，但主要在注意力机制和前馈网络两个部分进行了优化。

第一是 Multi-Head Latent Attention，也就是 MLA。传统多头注意力在自回归生成时需要缓存每一层的 Key 和 Value，长上下文下 KV Cache 会占用大量显存。MLA 通过低秩压缩，把 Key 和 Value 压缩成一个潜在向量，推理时主要缓存压缩后的表示，需要计算注意力时再进行映射，从而显著降低 KV Cache，同时尽量保留多头注意力的表达能力。

第二是 DeepSeekMoE。它将传统 Transformer 中的 FFN 替换为混合专家结构，每个 Token 不会经过所有专家，而是由路由器选择少量专家参与计算。DeepSeekMoE 还采用了细粒度专家划分和共享专家：共享专家负责学习通用知识，路由专家负责学习不同领域的专门知识。因此模型可以拥有很大的总参数量，但每个 Token 只激活其中一部分参数，从而降低实际计算量。

在 DeepSeek-V3 中，还加入了无辅助损失的负载均衡机制，减少传统 MoE 负载均衡损失对模型能力的干扰；同时采用 Multi-Token Prediction，让模型在训练时不仅预测下一个 Token，还预测后续多个 Token，以提高训练信号密度和模型性能。

DeepSeek-R1 的底层模型主要基于 DeepSeek-V3-Base，所以 R1 的核心创新更多是在后训练阶段。R1-Zero 直接通过 GRPO 强化学习激发推理能力，而正式版 R1 增加了冷启动数据、推理强化学习、拒绝采样和多阶段训练，改善了 R1-Zero 存在的语言混杂和可读性问题。

所以我会把 DeepSeek 的特点概括为：通过 MLA 降低推理时的 KV Cache，通过稀疏 MoE 降低大模型的实际计算成本，再通过强化学习提升复杂推理能力。

### Q5. 介绍一下transformer架构和lora原理

Transformer 是一种基于注意力机制的序列建模架构。它的核心是 Self-Attention，输入会分别映射为 Q、K、V，通过 Q 和 K 的点积计算不同 Token 之间的相关性，再对 V 进行加权聚合。

Transformer Block 通常由多头注意力、前馈网络、残差连接和 LayerNorm 构成。多头注意力可以从不同子空间学习语法、语义和指代等关系，FFN 则负责对每个 Token 的表示进行非线性变换。

原始 Transformer 包含 Encoder 和 Decoder，BERT 主要使用 Encoder，GPT 类模型使用带因果掩码的 Decoder-only 架构。Transformer 的优势是并行性强、能建模长距离依赖，主要问题是标准注意力的时间和空间复杂度都是序列长度的平方。



LoRA 是一种参数高效微调方法。它冻结预训练模型原始权重$W_0$，不直接对整个矩阵进行更新，而是把任务相关的参数增量表示成两个低秩矩阵的乘积，即 $\Delta W=BA$。

前向计算变成$W_0x+\frac{\alpha}{r}BAx$，训练时只更新 A 和 B，因此可以大幅减少可训练参数、优化器状态和显存占用。LoRA 一般应用在注意力层的 Q、K、V、O 投影或者 FFN 层。推理时还可以把 LoRA 权重合并回原模型，基本不会增加额外推理延迟。

它成立的核心假设是，大模型适配下游任务时，权重变化具有较低的内在秩。相比全量微调，LoRA 成本更低，但在任务差异很大或需要显著改变模型能力时，效果可能不如全量微调。
