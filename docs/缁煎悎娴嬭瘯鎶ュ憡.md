# ECOMMERCE-GUIDER 综合测试报告

## 1. 测试设计、执行过程与验收结论

### 1.1 测试目标

本轮验收确认后端 Agent 的核心能力是否真实生效：

1. 用户需求能被正确理解，复杂表达优先由 Doubao 生成结构化 `IntentPlan`；
2. 商品推荐必须来自真实商品库和 RAG 检索，不允许由大模型编造；
3. 多轮对话、事件记忆、指代解析、购物车工具、历史恢复和个性化都要能端到端运行；
4. 前端输出保持统一结构：`frontend_events`、`frontend_data`、`system_debug`；
5. 真实 SSE progress 能在主流程完成前先返回，避免前端空白等待；
6. 对无精确库存、预算不匹配、否定约束等情况，系统要给出积极导购式备选，而不是消极拒绝。

### 1.13 RAG、Prompt 与防幻觉验收

真实测试确认：

1. Doubao 不直接接触全量商品库，只基于后端传入的候选商品事实生成回复；
2. 商品名、价格、品牌、参数、增强字段均来自商品库；
3. 无库存时不编造商品，而是走相近备选或导购式引导；

### 1.14 鲁棒性与闭环引导验收

三层鲁棒性防护已经接入主流程：

1. 渐进检索容错：严格无结果时逐步放宽价格、子类目、否定约束或全库范围；
2. 无结果导购式引导：有备选就积极推荐相近商品并说明差异；
3. 全局异常安全网：异常时仍返回统一结构，避免前端崩溃。

智能下单闭环已验证：

- 1 件商品：提示可生成订单预览；
- 2-3 个 SKU：可汇总购物车；
- 4+ 件或大数量：提示确认商品和地址；
- 用户拒绝结算时进入冷却，不反复打扰。

#### 1.15.1 跨类目切换

测试目的：验证用户从一个商品类目切换到另一个完全不同类目时，系统不会被旧类目锁死。

测试输入：

```text
T1: 推荐一款拍照好的手机
T2: 我不看手机了，想看看休闲外套，通勤能穿的
```

预期结果：

1. T1 正确识别为 `数码电子/智能手机`；
2. T2 明确切换到 `服饰运动`，不能继续推荐手机；
3. T2 可展示服饰商品列表或商品详情，但商品必须来自服饰运动类目；
4. `system_debug` 中不应出现旧手机主题锁死导致的 `context_topic_lock`。

真实结果：

| 轮次 | 实际结果 |
|---|---|
| T1 | 推荐 OPPO、小米等拍照手机，类别为 `数码电子/智能手机` |
| T2 | 推荐 `p_clothes_032` 蕉下防晒衣，类别为 `服饰运动/防晒衣`，回复强调通勤外套使用场景 |

结论：通过。早期版本能切到服饰大类，但“休闲外套”子类识别不稳定，容易进入澄清；已在 `query_understanding.py` 中将“休闲外套”映射为当前库存里最接近的 `防晒衣`，并用回归测试保护。

#### 1.15.2 无结果处理

测试目的：验证没有 exact match 时，系统不会崩溃、不会返回空结果，而是给出真实相近备选或明确引导。

测试输入：

```text

```

预期结果：

1. 保留用户显式需求 `服饰运动/连衣裙`，不能把“连衣裙”静默改写成其他商品；
2. 如果库存没有连衣裙，进入 `no_result` 或 relaxed alternatives；
3. 返回 `alternative_products`，商品必须来自真实库存，且优先满足 500 元以内；
4. 回复应积极说明“我先为你挑几款更接近需求的选择”，而不是空泛道歉。

| 字段 | 实际结果 |

| 业务流程 | `no_result` |

### 1.16 真实耗时结论

本轮没有 timeout，但复杂轮次仍偏慢。主要原因是远程 Doubao 调用耗时，而不是本地 RAG 或前端事件构造。

| 场景 | 真实耗时 | Doubao 调用 | 说明 |
|---|---:|---:|---|
| 普通商品推荐 | 9-18s | 1-2 次 | 多数时间在回复生成 |
| 商品对比 | 22s 左右 | 2 次 | 意图计划 + 对比回复生成 |
| 反选防晒 fallback | 33s 左右 | 2 次 | 否定约束解析 + fallback 回复生成 |
| 连衣裙缺货 fallback | 46-58s | 2 次 | Doubao 意图解析偏慢，随后还要生成备选回复 |
| 多模态化妆品图 | 36s 左右 | 2 次 | 图片理解/意图计划 + 回复生成 |

结论：为了 Demo 稳定，前端必须使用 `curl -N` 或 Android 流式读取 SSE progress。后端已实现快速 progress events，真实 HTTP 观察中首条 progress 可约 0.1 秒到达；FastAPI TestClient 会缓冲，不适合验证首条进度。

## 2. 当前系统核心创新设计

### 2.1 Doubao-first IntentPlan

复杂、模糊、多动作用户表达由 Doubao 解析为结构化 `IntentPlan`，系统再按动作序列执行。只有非常简单的模板表达走本地规则，例如“推荐xxx商品”“想要xxx商品”“选择一款xx”“预算是xx”。

已验证表达：

- “刚才加购的防晒不要了，清空购物车，重新挑选一款适合通勤和旅行的背包”
- “把第一款和第二款防晒乳都加入购物车，各加5瓶”
- “第一款和第二款哪个更适合拍风景？”
- “我觉得第二个不错，给我介绍下”

设计亮点：意图识别不再只输出一个 intent，而是输出可执行动作序列，支持工具动作和检索动作混排。

### 2.2 Grounded RAG 与商品增强字段

商品推荐由本地商品库、结构化过滤、向量召回、重排序和后处理完成。Doubao 不直接凭空挑商品，只能基于后端给出的候选商品事实生成回复。

增强字段参与 query enhancement、召回、重排、推荐理由、商品详情和商品比较。所有增强字段仍然属于已有商品事实，不能引导 Doubao 编造不存在的价格、参数、优惠或库存。

### 2.3 事件记忆

系统新增事件记忆，解决“第一款/第二个/刚才那个”在多轮中的稳定回溯问题。

事件类型：

- 推荐事件：记录一次商品列表的稳定顺序；
- 商品详情事件：记录当前关注的商品；
- 对比事件：记录对比商品集合；
- 购物车事件：记录加购、删除、清空、结算等工具动作。

### 2.4 层次化个性化

个性化不是单一画像，而是分层设计：

1. 用户历史画像；
2. 领域风格个性化；
3. 相似历史用户协同过滤；
4. 购物车侧同类商品个性化；
5. 隐私保护个性化。

当前用户明确需求始终是硬约束；用户画像、协同过滤和购物车画像只作为软约束。

### 2.5 progress events 与耗时统计

progress events 是前端等待态，不是模型推理链。它只显示美化后的处理状态，例如“正在理解需求”“正在商品库中筛选”“正在组织回复”。  
`system_debug.运行耗时统计` 会展示每个模块耗时、模型调用次数、模型调用总耗时、最慢 Top 模块和主流程总耗时。

### 2.6 多模态图片商品匹配

当前多模态能力支持：

- JSON `image_path`；
- multipart `/api/chat/stream/upload`；
- Doubao 图像理解；
- 本地测试图 fixture 兜底；
- 商品图相似度弱匹配；
- 图文融合检索；
- 只返回真实库存商品。

## 4. 仍需关注的问题

1. 真实 Doubao 耗时仍偏长，复杂轮次约 30-60 秒。主要耗时来自远程模型调用，尤其是意图计划和回复生成各调用一次时。

3. FastAPI TestClient 会缓冲 SSE，不适合验证首条 progress 的真实到达时间；请用 `curl -N` 或 `scripts/http_stream_observer.py`。
4. 本地 `storage/user_history` 中仍有一些旧测试历史目录；正式演示时建议优先使用专门构造的用户目录，避免旧测试数据影响协同过滤样本。
