### 1.4 模拟用户生态系统 (User History Ecosystem)

系统在 `storage/user_history/` 中预置了 **26 个模拟用户**，共计 **109+ 个会话文件**、**800+ 轮对话**。这些用户是系统个性化能力的核心基础设施，支撑协同过滤、隐私模式验证、购物车个性化测试三大功能。（细节见后Sec 11)

#### 用户数据的使用方式

这些模拟用户在系统运行时的使用路径：

1. **新用户冷启动**：当用户说"我是油皮/预算100/学生党"时，系统提取 `structured_profile` 中的自述信息，在八人设中找到最匹配的人设，参考其 `system_adaptation_strategy` 的渐进适应节奏

2. **协同过滤（4+ 轮后触发）**：`PersonalizationService` 将当前用户与 24 个历史用户的 `structured_profile` 做余弦相似度计算，选出 Top-3 相似用户，将其回复风格作为 few-shot 示例注入 prompt

3. **购物车个性化**：`CartAwarePersonalization` 读取预置用户的购物车内容和 `semantic_memory`，命中 30+ 条本地搭配规则（如 digital_tony 的 Apple 生态规则），对检索结果做 rerank 加成

4. **隐私模式切换**：用户可通过自然语言（"不要保存聊天""可以保存聊天""关闭个性化"）实时切换隐私模式，切换逻辑参考四个隐私验证用户的行为模式

5. **`--resume` 恢复**：指定 `--resume` 或 `resume: true` 时，`UserHistoryStore.restore_state()` 从磁盘读取完整的 `state_snapshot`（含购物车、约束、推荐记录、事件记忆），恢复到内存中的 `SessionState`

### 2.7 边界情况专项测试（2026-06-03 补充）

`1.3 测试维度` 中列出的三项边界情况此前只列出了测试方向，没有写清楚可复现的步骤和实际结果。本节补齐最新真实测试结论，并已在 `backend/tests/test_api_flow.py` 增加对应回归测试。

#### 2.7.1 跨类目切换

**测试目的**: 验证用户从一个商品类目切到完全不同类目时，系统不会被上一轮旧类目锁死。

**测试输入**:

```text
T1: 推荐一款拍照好的手机
T2: 我不看手机了，想看看休闲外套，通勤能穿的
```

**预期结果**:

- T1 识别为 `数码电子/智能手机`；
- T2 切换到 `服饰运动`，不能继续推荐手机；
- T2 推荐或展示的商品必须来自服饰运动类目；
- `system_debug` 中不能出现旧手机主题锁死导致的错误。

**实际结果**:

| 轮次 | 实际输出 |
|------|----------|
| T1 | 推荐 OPPO、小米等拍照手机，类别为 `数码电子/智能手机` |
| T2 | 推荐 `p_clothes_032` 蕉下防晒衣，类别为 `服饰运动/防晒衣`，回复强调通勤外套场景 |

**结论**:  通过。早期版本能切换到服饰大类，但“休闲外套”子类识别不够稳定，容易进入澄清。本轮已将“休闲外套”映射到当前库存里最接近的 `防晒衣`，并通过回归测试保护。

#### 2.7.2 无结果处理

**测试目的**: 验证商品库没有 exact match 时，系统不会崩溃或返回空结果，而是提供真实相近备选或明确引导。

**测试输入**:

```text
推荐一款连衣裙，500以内
```

**预期结果**:

- 保留用户显式需求 `服饰运动/连衣裙`，不能把“连衣裙”静默改写成其他商品；
- 库中无连衣裙时进入 `no_result` 或 relaxed alternatives；
- 返回真实库存备选，优先满足 500 元以内；
- 回复保持积极导购语气，不以消极道歉开头。

**实际结果**:

| 字段 | 实际输出 |
|------|----------|
| 业务流程 | `no_result` |
| 保留子类 | `连衣裙` |
| 备选商品 | `p_clothes_006` 运动长裤 ¥349、`p_clothes_029` 连体泳衣 ¥299、`p_clothes_034` 运动内衣 ¥329 |
| 前端输出 | `show_reply` + `show_products`，不再额外触发 `show_error` |

**结论**:  通过。真实测试耗时约 65.8 秒，主要来自 Doubao 意图计划和无结果回复生成两次远程调用；功能正确，但后续可继续压缩 fallback prompt 和模型调用次数。

#### 2.7.3 大数量购物车

**测试目的**: 验证购物车中商品较多时，查看、加购、删除、修改数量、下单引导和 `system_debug` 是否仍然稳定。

```bash
curl -X POST http://127.0.0.1:8000/api/cart/add \
  -H "Content-Type: application/json" \

curl -X POST http://127.0.0.1:8000/api/cart/add \
  -H "Content-Type: application/json" \
  -d '{"session_id":"boundary_bigcart","sku_id":"p_food_003","quantity":8}'
```

**测试输入**:

```text
T1: 查看购物车
T2: 把购物车里的第一款改成2瓶
T3: 把购物车里的第二款删掉

```

**实际结果**:

| 步骤 | 实际输出 |

**结论**:  通过。真实复验中发现结算回复曾重复拼接“下单闭环引导”，已在 `response_generator.py` 修复：进入 `checkout` 后只返回订单预览，不再继续追加购买引导。

## 3. 层次化回复个性化

### 3.1 协同过滤个性化

**测试方法**: 同一查询"帮我推荐一款精华"，发给两个风格迥异的用户，对比回复风格差异。

| 维度 | 小美 (xiaomei_beauty) | Lily Pro (lily_beauty_pro) |
|------|----------------------|---------------------------|
| **人设** | 20岁学生, 预算≤100, 萌系小白 | 32岁职场, 预算500+, 成分党 |
| **回复风格** | 软萌劝导: "要不要我帮你专门筛选100以内不含酒精的温和款精华呀？" | 专业成分分析: "采用透明维C+玻色因的组合，兼顾提亮匀肤和淡纹抗初老" |
| **价格敏感** | 强调预算超标，主动提出降级筛选 | 价格直接陈述，不做预算预警 |
| **CF相似用户** | victoria_beauty(0.87), beauty_lily, lily_beauty_pro | victoria_beauty(0.87), xiaomei_beauty, beauty_lily |
| **协同过滤效果** | 参考了小白型用户的简洁解释风格和萌系语气 | 参考了专家型用户的成分剖析深度和精准措辞 |

**关键发现**:
-  协同过滤正确找到了相似用户，相似度排序合理
-  回复风格差异化明显：小美得到"呀/哦"语气词和预算关怀，Lily得到成分浓度和技术分析
-  两个用户因库存限制得到了相同的3款产品，但推荐理由和定价引导不同

### 3.2 领域个性化

**测试方法**: 检查不同领域的"导购角色"和解释重点是否随领域自动切换。

| 用户 | 领域 | 导购角色 | 解释重点 |
|------|------|----------|----------|
| 张工 (zhanggong_digital) | 数码电子 | 数码电子导购小哥 | 预算、核心功能、参数/体验、适合人群、短板 |
| 王经理 (wangjingli_food) | 食品饮料 | 食品饮料导购 | 品质/等级、包装体面、送礼适配、品牌口碑 |
| 小美 (xiaomei_beauty) | 美妆护肤 | 美妆护肤导购小姐姐 | 肤质适配、质地肤感、成分/功效边界、使用场景 |
| 大刘 (daliu_sports) | 服饰运动 | 服饰运动导购 | 功能性、耐用度、面料/做工、透气/速干 |

**关键发现**:
-  四领域各有独立的导购角色和解释重点，随用户查询的领域自动切换
-  张工的回复非常简短直接——"拍照、续航、游戏性能，还是性价比？"——体现极客风格
-  王经理的回复注重品质和体面——"包装精致有档次，品牌口碑出众，完全能满足商务送礼的品质和体面需求"

### 3.3 基于用户历史的个性化

**测试方法**: 检查用户的 profile_summary_text 和历史证据是否被用于个性化回复。

| 用户 | 会话数 | 历史证据数 | 个性化效果 |
|------|--------|-----------|-----------|
| alex_sports | 29 sessions | 5条 evidence | 回复"结论先行+简洁"风格，优先推荐 Nike 品牌 |
| beauty_lily | 4 sessions | 协同过滤起效 | 通过 CF 参考相似用户风格，预算偏好尚不稳定 |
| xiaomei_beauty | 0 sessions | 依靠 structured_profile | 冷启动个性化：自行声明年龄/肤质/预算 → 系统调整语气和价格引导 |

**关键发现**:
-  有充足历史的用户 (alex_sports) 个性化效果最好，价格偏好、品牌偏好、决策风格均已稳定
-  冷启动用户 (xiaomei_beauty) 通过 structured_profile 仍获得了个性化——预算提醒和可爱语气
- ⚠️ 4 sessions 的 beauty_lily 画像还不够稳定，profile_summary 仅提到"面霜需求"

## 4. 购物车商品侧个性化

### 4.1 Apple 生态推荐

**测试**: digital_tony（购物车: iPhone + MacBook）

**结果**:  命中 3 条搭配规则：
- `phone_accessory_ecosystem`（手机→生态配件）
- `brand_ecosystem_Apple 苹果`（品牌生态）
- `apple_macbook_ecosystem`（MacBook→全生态）

推荐结果全部为 Apple iPad，强调"和你购物车里的iPhone、MacBook无缝联动，很适合日常记笔记、轻度办公和影音娱乐"。排序加成 +0.25（品牌搭配 + 类目搭配 + 标签相近 + 价格带匹配）。

### 4.2 健康早餐搭配

**测试**: food_emma（购物车: 桂格燕麦 + 金典牛奶 + 北大荒蜂蜜）

**结果**:  命中 `breakfast_bundle` 和 `gift_quality_bundle` 规则。推荐了方便面等速食早餐，并提到"可以搭配你购物车里的燕麦、牛奶和蜂蜜，组合出更丰富的早餐搭配"。标签中"价格敏感"使推荐偏向低价位食品。

### 4.3 购物车标签抽象

**测试**: 检查标签是否正确从购物车商品中抽象。

| 用户 | 购物车商品 | 抽象标签 |

## 9. 系统鲁棒性 (Robustness)

> 这是系统第五个核心创新点，2026-06-02 实现并测试

### 9.1 设计目标

三层防护机制确保系统在任何情况下都能给出恰当回复：
- **Layer 1: 检索容错** — 严格过滤 0 结果时，渐进放宽约束找到替代品
- **Layer 2: 响应容错** — 无匹配时生成智能引导回复，说明库存范围和替代方向
- **Layer 3: 全局安全网** — 任何模块异常都被捕获，生成兜底回复，不暴露内部错误

### 9.2 Layer 1: 检索渐进容错

**实现**: `app/retrieval/fallback.py` — `RetrievalFallback.progressive_retrieve()`

四级渐进放宽策略：

| 步骤 | 放宽内容 | 触发条件 |
|------|----------|----------|
| Step 0 | 严格检索 | 首次尝试 |
| Step 1 | relaxed_price | 移除价格 min/max 约束，取价格最接近原预算的候选 |
| Step 2 | relaxed_sub_category | 进一步放宽子类目，同类目中宽泛搜索 |
| Step 3 | relaxed_negative | 移除否定硬过滤（仅保留软评分降权） |
| Step 4 | broad_search | 全类目搜索，移除 category/sub_category 约束 |

每一步的放宽详情（放宽了什么、找到多少候选、最接近价格）记录在 `FallbackResult` 中，供回复生成时精确告知用户。

**测试 R1: 超低预算 → 价格放宽**

```
输入: "推荐一款蓝牙耳机，100以内"
Step 0: 严格检索 → 0个候选（最低价耳机¥1499）
Step 1: 放宽价格  → 2个候选（¥1499, ¥1799）
结果: 展示2个替代品 + 说明"两款都略高于你100元的预算，最接近的¥1499"
```

**测试 R2: 严格排除 → 多重放宽**

```

Step 0-2: 逐步放宽价格和子类目 → 候选出现
结果: 展示1个替代品 + 说明"完全符合你不要日系、不含酒精的要求，只是价格略高于预算"
```

### 9.3 Layer 2: 响应容错

**实现**: `response_generator.py` — `_no_result_response()` 重写 + 新增 `_get_category_guidance()`

- 有替代品 + fallback 信息 → 精确说明放宽了什么："比你XX元预算略高，最接近的¥XX，在功能上最贴合你的需求"
- 有替代品 + 无 fallback 信息 → 通用积极引导："我先为你挑了几款更接近需求的选择"
- 完全没有匹配 → 调用 `_get_category_guidance()`，列举该领域的可用子类目和价位范围，引导用户调整需求

**测试 R3: 库存不存在的品类（连衣裙）**

## 10. 智能下单闭环引导 (Closing Loop)

> 这是系统第六个核心创新点，2026-06-02 实现并测试

### 10.1 设计目标

不能与用户无限对话。当用户完成选购（加购）且未表达新需求时，系统应主动推动业务结束——确认商品、填写地址、发起结算。同时绝对不能在用户还在浏览/推荐阶段误触发。

**核心约束**:
- ✅ 只在购物车有商品且用户完成选购后触发
- ✅ 绝对不在纯推荐/商品详情/对比阶段触发
- ✅ 用户拒绝后冷却 2 轮，不追问
- ✅ 购物车新增商品时重新触发，汇总最新信息
- ✅ 根据商品数量自适应文案（1件/2-3件/4+件）

### 10.2 架构设计

```
ShoppingAgent._maybe_trigger_closing()
  ├── 反查 ProductRepository 获取商品名和价格
  ├── ClosingGuide.should_trigger()         # 五条件判断
  ├── ClosingGuide.build_guidance_context() # 构造引导上下文和 Doubao prompt hint
  └── ResponseGenerator.generate(closing_context=...)
        └── _cart_response() + _closing_guidance_text()  # 拼接引导文案

ShoppingAgent._is_closing_acceptance()  # 用户接受 → 自动转 CHECKOUT flow
ShoppingAgent._is_closing_decline()     # 用户拒绝 → 记录冷却时间戳
```

**触发五条件**（全部满足才触发）:
1. 购物车非空
2. 当前轮是购物车操作（cart_add / cart_view / cart_update）
3. 当前消息中无新购物需求信号（30+ 信号词：推荐/筛选/比较/还有/再看看 等）
4. 用户未刚拒绝（2 轮冷却期）
5. 购物车内容与上次触发时不同（有新商品时重新触发，避免重复相同引导）

### 10.3 测试结果

| 场景 | 查询序列 | 预期 | 结果 |
|------|----------|------|------|
| A: 纯推荐 | "推荐一款手机" | 不触发 | ✅ 正确不触发 |
| B: 加购触发 | "推荐跑鞋" → "第一款加入购物车" | 触发引导 | ✅ "如果确定要买「特步160X...」告诉我收货地址和联系方式，我就可以帮你生成订单预览啦。还想加其他商品也可以继续说哦～" |
| C: 商品详情 | "推荐精华" → "第一个介绍一下" | 不触发 | ✅ 正确不触发 |
| D: 多商品 | 推荐防晒→加购→推荐卸妆→加购 | 两次都触发 | ✅ T1: "确定要买「安热沙...」" T2: "你购物车里现在有2件商品（安热沙...、芳珂...），合计¥296。需要我帮你汇总订单、填写收货地址吗？" |

### 10.4 自适应文案示例

|-----------|----------|

### 10.5 评价

- ✅ 触发时机精准——纯推荐、商品详情等非购物车操作绝不误触发（30+ 信号词拦截）

#### 协同过滤工作原理

当新用户与系统对话积累超过 4 轮后，`PersonalizationService` 自动触发协同过滤分析：

1. **特征提取**：从当前用户的 `structured_profile` 中提取 8 个维度的特征向量（说话风格、语言风格、价格偏好、类别偏好、品牌偏好、排斥条件、决策风格、信息关注点）
2. **相似度计算**：与 24 个历史用户的特征向量逐一比较，计算余弦相似度
3. **Top-K 选择**：选出相似度最高的 3-5 个用户作为"相似人群参考"
4. **风格迁移**：在生成回复时，将相似用户的**回复风格**（语气词、解释深度、推荐策略）作为 few-shot 示例注入 prompt，但不复制他们的**历史内容**

实际测试验证：小美（萌系小白）的协同过滤相似用户为 victoria_beauty(0.87)、beauty_lily、lily_beauty_pro；Lily Pro（成分专家）的相似用户则为 victoria_beauty(0.87)、xiaomei_beauty、beauty_lily。两人虽然得到相同的产品推荐（库存限制），但回复风格迥异——小美得到"要不要我帮你专门筛选100以内不含酒精的温和款精华呀？"，Lily 得到"采用透明维C+玻色因的组合，兼顾提亮匀肤和淡纹抗初老"。

- **`semantic_memory`**：语义计数——`category_counts`（类目出现次数）、`feature_counts`（功能词出现次数+证据数）、`brand_counts`（品牌出现次数）、`price_signals`（价格信号列表）、`negative_constraint_counts`（否定约束出现次数）
- **`memory_cards`**：置信度加权的偏好卡片（scope + confidence + evidence_count），当 semantic_memory 中某特征的 evidence_count 超过阈值时自动晋升
- **`privacy_settings`**：隐私模式配置

### 12.2 六大创新点总览

1. **层次化回复个性化** — 协同过滤（24 用户）+ 领域风格（4 领域）+ 历史画像，三层叠加。同一查询"推荐精华"，小美得到萌系预算关怀，Lily 得到成分浓度分析。
2. **购物车商品侧个性化** — 30+ 条本地搭配规则（精华→面霜眼霜面膜、手机→同品牌耳机手表充电宝、MacBook→Apple 全生态、跑鞋↔速干服饰 等）+ Doubao fallback 处理跨类目复杂搭配。
3. **商品增强字段** — 每件商品 6 个增强字段（product_highlight / highlight_short / highlight_detail / suitable_scenarios / target_user_tags / non_standard_query_tags），"拍照好的手机"精确命中。
4. **多模态图文融合** — Doubao VLM → 结构化 JSON → fuzzy inventory mapping（三级匹配）→ 图文融合检索。支持 multipart/form-data 上传。
5. **系统鲁棒性** — 检索四级渐进容错（价格→子类→否定→全类目）+ 越界智能引导（25 项检测 + 个性化重定向）+ 全局异常安全网。
6. **智能下单闭环引导** — 五条件精准触发 + 自适应文案（1件/2-3件/4+件）+ 拒绝冷却 + 增量重新汇总。在正确时机推动业务结束。
